15.10.2026. Fisker Ocean 2023 EU / Ocean OS 2.1 зі слів власника; Samsung Galaxy S24 Ultra / Android 16; Vgate vLinker FD-IOS BLE, банер ELM327 v2.2. Аудит коду: `7da7e65c90e00bd647746464be7f4f86e74b5467`, гілка `diagnostics/can-overflow-root-cause`, PR #2. Основне вимірювання - прикріплений експорт, а не попередні припущення.

## Рішення і п'ять відповідей

**Математика і реалізація 11-бітних масок правильні. Дефекту Android-коду, який пояснював би нуль усіх інших ID, не виявлено. Правильне пропускання цільових ID реальною прошивкою Vgate ще не доведене: відфільтровані вікна не містять жодного позитивного зразка.**

| Запитання | Відповідь і впевненість |
|---|---|
| Чи правильно працює фільтрація? | Формування команд і покриття правильні, висока впевненість. Виключення спостережуваного ID узгоджується з логом; апаратне включення інших ID не перевірене. |

## 2. Математика всіх 11 масок

ELM acceptance rule: `(id & mask) == (filter & mask)`. У наших фільтрах усі біти поза маскою нульові, тому права частина дорівнює `filter`. Біт маски 1 вимагає збігу, біт 0 його ігнорує [1,2].

| № | ATCM | ATCF | Діапазон включно | ID |
|---|---|---|---|---:|
| 1 | 400 | 400 | 400-7FF | 1024 |
| 2 | 600 | 200 | 200-3FF | 512 |
| 3 | 700 | 100 | 100-1FF | 256 |
| 4 | 780 | 000 | 000-07F | 128 |
| 5 | 7C0 | 080 | 080-0BF | 64 |
| 6 | 7E0 | 0C0 | 0C0-0DF | 32 |
| 7 | 7F0 | 0F0 | 0F0-0FF | 16 |
| 8 | 7F8 | 0E0 | 0E0-0E7 | 8 |
| 9 | 7FC | 0EC | 0EC-0EF | 4 |
| 10 | 7FE | 0EA | 0EA-0EB | 2 |
| 11 | 7FF | 0E8 | 0E8 | 1 |

Сума: `1024+512+256+128+64+32+16+8+4+2+1 = 2047`. Повний 11-бітний простір містить **2048** значень, `000-7FF`; після виключення одного лишається 2047. Покрито також `000`, а не лише `001-7FF`.

Доведення без перебору: для будь-якого `id != 0E9` існує єдиний найстарший біт, у якому вони відрізняються. Одна група вимагає спільного старшого префікса і протилежного значення саме цього біта; молодші біти ігноруються. Тому кожний інший ID потрапляє рівно в одну групу, а `0E9` - у жодну.

Додатково виконано незалежний повний перебір 2048 значень для всіх 11 комбінацій. Python порівнює окремі біти, Java перевіряє згенерований Android-план проти вручну заданої таблиці. Результат: єдина прогалина `0E9`, максимальна кратність 1.

## 3. Семантика команд і реальна послідовність

| Команда | Роль у перевірці |
|---|---|
| `ATCM` / `ATCF` | Маска й шаблон acceptance filter. ELM/OBDLink описують відбір на стороні адаптера; внутрішню реалізацію Vgate з логу визначити неможливо. |
| `ATMA` | Приймання без запиту ECU; ручні CM/CF обмежують потік. Назва Monitor All не означає скасування явно заданої маски. |
| `ATSP6` | Формат 11-bit / 500 kbit/s, не вибір іншої фізичної мережі. |
| `ATCAF0` | Сирі CAN data bytes без ISO-TP autoformatting. |
| `ATCFC0` | Вимкнений автоматичний flow control. |
| `ATCSM1` | Silent monitoring, зокрема без ACK; `CSM0` не дозволено. |
| `ATD1` | Виведення DLC; не плутати з `ATD` - скиданням defaults. |
| `ATCRA` без аргументу | Повернення default receive filters; це не reset ECU і не відкриття всіх ID. |

Спочатку один `ATZ`, потім конфігурація, `ATSP6`, CAF0/CFC0/CSM1, DLC і контроль зі CM000/CF000. Для кожної групи: **CM -> prompt OK -> CF -> prompt OK -> ATMA -> stop/prompt**. Обидві настройки завершуються перед ATMA. Немає нормативної вимоги завжди ставити CF раніше CM: у datasheet є приклади обох порядків [1]. Проміжний стан маски не моніториться.

Між групами немає ATZ, зміни протоколу, ATCRA або команди, що мала б повертати defaults. Єдиний ATCRA стоїть **після** всіх вимірювань, після ATD0. Попередні точні CRA з режиму ідентифікації не пояснюють цей лог: нова сесія починається з ATZ і явно переписує CM/CF. Аудит не викликає MR/MT, які могли б змінити приймальний відбір.

Для STN/OBDLink CF/CM документовані як hardware filters [2]. Linux can327 також розрізняє їх і фільтрацію в host [6]. Vgate декларує AT/ST-сумісність [3], але її banner не ідентифікує точну збірку firmware. Ми підтвердили придушення вихідного потоку, **не місце відсікання всередині чипа**. Відповідь OK і відсутність сторонніх ID перевіряють негативну умову; відсутність усіх кадрів не перевіряє позитивну.

У filtered-групах `rawAsciiPrefix` містить усі отримані 10 байт. Тому гіпотеза «BLE приніс інші кадри, але parser їх загубив» цьому конкретному експорту суперечить. Втрату **до callback**, помилку firmware або відсутність фізичного трафіку лише з host-логу виключити не можна.

Відтворення через реальні `ElmChannel` і `CanCapture` пропустило всі 2047 синтетичних ID, з фрагментацією заголовка, через 11 послідовних чисто завершених вікон. Це перевірка нашого коду, а не емуляція внутрішніх помилок Vgate.

Методичні обмеження лишаються: немає позитивної перевірки приймання вибраного ID Vgate; невідомі стани HVAC/awake; вікна короткі й не одночасні. Вони не обґрунтовують косметичної зміни Android або нового APK.

## 5. 29-бітний CAN

Номінально сімейство vLinker FD+ підтримує ELM/STN CAN-протоколи [3]. Стандартна конфігурація 29-bit / 500 kbit/s - **ATSP7**, 8 hex digits для CM/CF, ATH1, сирий формат, DLC і silent monitoring [1,2]. Для пасивного приймання ATCP, ATSH і діагностичний payload не потрібні.

Важливі межі:

- У наданому JSON тільки протокол 6. Поточний Android-аудит не перевіряє 29-bit; `ATSP7` заблоковано його окремим allowlist. Це заявлена межа режиму, не знайдений баг.
- На деяких ELM-конфігураціях монітор може приймати і standard, і extended frames [6]. Не слід вважати, що сама цифра 6 довела фізичну відсутність extended frames. У наших filtered raw-вікнах немає жодних frame lines узагалі.
- Fiskeretta містить `discover_ecus_29bit()`, але ця функція **надсилає запити** і не є доказом успішного 29-бітного вимірювання Ocean. Її vehicle-проби в наше рішення не переносилися [4].
- DBC puddletools має extended-marker `0x80000000` при малих числових ID. Це опис формату файла, а не незалежний raw CAN trace з IDE bit. З нього не робиться висновок про реальний 29-бітний HVAC [5].
- Підтвердженого публічного raw trace 29-бітних **HVAC** кадрів для цього Ocean/версії не знайдено. Це прогалина доказів, не доказ відсутності.
- ATSP7 змінює формат/налаштування того самого CAN-контролера; він не підключає EV-CAN або іншу пару контактів за gateway. 29-bit CAN і CAN FD - різні властивості. Назва адаптера FD не доводить підтримку CAN FD frames.

Безпечна пасивна проба можлива з підтвердженим CSM1/CFC0, без auto-search, без payload і з припиненням на overflow/error. Конкретну прошивку Vgate так на автомобілі ще не перевіряли. Зручніше включити 11/29-bit та IDE у наступний незалежний native-запис, не випускаючи APK лише для зміни ATSP.

**Не встановлено:** повний актуальний OEM network topology/pinout для Fisker Ocean 2023 EU, точна routing table gateway, конкретні робочі HVAC IDs/DIDs і бітові розкладки, доступність потрібних повідомлень на OBD у locked/sleep. Законно відкритої повної OEM-схеми, яка закривала б ці питання, під час перевірки не знайдено. Схеми Fisker Karma не використовуються як документація Ocean.

Суттєва різниця: адресна діагностика ECC означає, що gateway може маршрутизувати **запит/відповідь**. Вона не означає прозорого дублювання штатних команд ICC -> ECC на роз'єм OBD. Нуль діагностичних відповідей під час пасивного слухання нормальний, якщо жоден tester не надсилає запит.

Публічний код підтверджує ідентифікацію ECC/діагностику; перевіреної відкритої карти температури салону, setpoint, fan/heater feedback або start/stop/wake для нашої збірки немає. Заяви OceanLink Pro про preconditioning пов'язані з конкретними PKC/аксесуаром [12]; не можна переносити їх на довільний APK, Vgate або робити висновок про PKC лише з напису OS 2.1.

| 4 | Інший формат/протокол або інша фізична CAN | 29-bit тут не тестувався; внутрішніх шин кілька. | Валідні 11-bit кадри підтримують правильність 500 kbit/s для спостережуваного трафіку. Немає raw-доказу 29-bit HVAC. Формат не відкриває іншу шину. |
| 5 | Втрата в Android parser / sequence / prompt | Загалом можлива в такому транспорті. | Тут усі отримані bytes лише stop/prompt, invalid=0, write/prompt чисті, позитивний host replay всіх ID успішний. Низька ймовірність саме цієї причини. |

Мережеві гіпотези 1 і 4 можуть поєднуватися: повідомлення існують на іншій шині, а gateway їх не транслює. Немає підстав оголошувати Vgate несправним або HVAC фізично відсутнім.

## 8. Альтернативи і межа доцільності

| Підхід | Оцінка |
|---|---|
| CM/CF на наявному Vgate | Правильний спосіб зменшити output. Позитивне включення перевіряти відомим трафіком на ізольованому стенді або незалежним logger на тій самій лінії. |
| 2-5 с і повторення у стабільному стані | Допомагає рідкісним пакетам, але не усуває gateway і не перевіряє включення маски, якщо все порожнє. Не найсильніший наступний експеримент. |
| ST-фільтри Vgate | STN документує pass/block filters і `STM` з поточними фільтрами; `STMA` моніторить усе [2]. Vgate заявляє сумісність, конкретна підтримка невиміряна. Це не готова перевірена заміна. |
| Інший ELM через USB або Bluetooth Classic | Змінює output-транспорт, але не фізичну мережу й не routing gateway. За чисто порожніх filtered-вікон немає доказової причини купувати. |
| Позичений native CAN/CAN FD logger | Дає IDE, фізичні timestamps, error/drop counters і контроль на тій самій лінії. Потрібен для відокремлення фізичного нуля від інтерпретатора і для порівняння мереж. |
| Прямий внутрішній CAN через сервісний breakout | Обґрунтований шлях дослідження, якщо внутрішній HVAC-трафік не потрапляє на OBD. Спочатку правильний pinout, швидкість і listen-only, без вгадування контактів. |
| Документована діагностика ECC | Корисна для станів/параметрів, коли є перевірена специфікація. У цьому етапі запити ECU не виконувалися. Ідентифікація версії не дорівнює live climate telemetry або обігріву. |

## 9. Один наступний практичний крок

**Завдання виконавцю:** один синхронний пасивний запис діагностичного OBD і внутрішньої EV-CAN із двома штатними циклами клімату OFF -> ON -> OFF. Мета - вибрати фізичний шлях дослідження, не запускати дистанційний обігрів.

1. Позичити або використати сервісний двоканальний native logger з підтвердженим listen-only, записом 11/29-bit з IDE, timestamps, error/drop counters; бажано CAN FD capability для невідомого внутрішнього сегмента. Покупка не потрібна на цьому етапі.
2. До підключення виконавець підтверджує OEM/сервісною схемою конкретного автомобіля EV-CAN H/L, роз'єм і швидкість. Публічні номери Spider pins не використовувати як готову інструкцію. Канал A - стандартна CAN-пара OBD 6/14; канал B - підтверджена внутрішня EV-CAN, обидва через коректний сервісний breakout, без додаткової термінації внутрішньої шини.
3. На обох каналах тільки silent/listen-only: TX/ACK/active probing вимкнені. На OBD nominal 500 kbit/s; на B параметри за схемою/пасивним визначенням. Не вмикати auto-baud, що надсилає проби. Для CAN FD data bitrate також має бути визначений, не вгаданий.
4. Автомобіль стоїть у P, у звичайному увімкненому стані. Людина змінює клімат лише штатним екраном. Записати двічі цикл: 20 с OFF, 20 с ON з фіксованими setpoint/fan, 20 с OFF. Разом 120 с безперервно на обох каналах; записати точні моменти перемикань і видимі стани екрана.
5. У першому OFF та ON за потреби запустити **наявний** CAN Network Audit Vgate для одночасного порівняння через passive OBD splitter. Це контроль іншим приладом, а не повторна боротьба з `0E9`. Жодного ECU tester/сканера, який генерує запити, паралельно не запускати.
6. Передати raw trace обох каналів з `timestamp/channel/IDE/RTR/DLC/data`, частотами ID, CAN error/drop counters, настройками logger і часовими позначками OFF/ON. ID не обрізати до 11 біт; extended ID з малим числовим значенням визначати за IDE.

| Отриманий результат | Практичне рішення |
|---|---|
| На A лише відомий ambient ID, на B багато трафіку і повторювана зміна з кліматом | Gateway/розділення мереж підтверджені для перевірених станів. Подальший аналіз операційного HVAC вести на B; Vgate/OBD залишити для діагностики. |
| На A є інші 11-bit кадри у відповідних вікнах/масках, Vgate їх не показує | Пріоритет - позитивна стендова перевірка firmware/filter inclusion Vgate і host timing. Не оголошувати іншу шину причиною. |
| На A є extended frames з IDE=1 | 29-bit доступний на цій фізичній лінії. Перевірити його кореляцію з кліматом; лише після цього обґрунтовано додавати окремий 29-bit Android-режим. |
| Інші кадри A з'являються лише поза 500-мс вікнами | Причина пропуску - час вибірки; потрібні довші прицільні вікна, а не заміна обладнання. |
| На B немає коректного трафіку або є drops/errors | Спершу перевірити підключення, швидкість і стан авто. Такий запис не є доказом відсутності HVAC або gateway restriction. |

**Критерій успішної сесії:** придатні без втрат синхронні записи, які показують, на якій лінії доступні кандидати HVAC і чи присутні вони на OBD у тих самих умовах. Повторна кореляція OFF/ON - лише підстава вибрати кандидатів, ще не декодування і не дозвіл передавати CAN-команди.

Для справжнього дистанційного обігріву після цього окремо потрібні підтверджені start/stop, дозволений шлях авторизації, locked/sleep wake, feedback, vehicle timeout і safety telemetry. Жоден із них цей пасивний аудит не довів; обігрів лишається заблокованим.

## 10. Довідкова пасивна конфігурація 29-bit

Це специфікація для окремої контрольованої перевірки виконавцем, **не проведений тест і не функція поточного APK**. Кожну команду надсилати лише після prompt попередньої; на неочікувану відповідь припинити пробу.

```text
ATZ
ATE0
ATL0
ATS1
ATH1
ATSP7
ATCAF0
ATCFC0
ATCSM1
ATD1
ATDPN          (очікується 7)
ATCM00000000
ATCF00000000
ATMA          (до 5 с або першого overflow/error/prompt)
```

Зберігати сирий ASCII, включно з 8-digit або розбитими на чотири байти заголовками. Поточний Android parser для цього не підходить. Якщо monitor ще активний, перервати одним символом, наприклад `!`, і дочекатися prompt до 1 с; якщо prompt уже був, stop не надсилати. Не використовувати порожній CR на idle prompt. Не повторювати після overflow автоматично. Після підтвердженого stop повернути `ATSP6`, `ATD0`, `ATCRA`, `ATCAF0`, `ATCFC0`, `ATCSM1` з prompt/OK, потім від'єднатися. За невідомого стану каналу не надсилати нові команди.

Дозволені лише локальні настройки і monitor; жодних hex payload, ATSH/ATCP, ECU Session/Reset, Security Access, Routine Control, write/flash або authorization bypass. Навіть позитивний результат ATSP7 описуватиме тільки підключену OBD-пару, не всі мережі автомобіля.

## 11. Відтворюваність і перевірки

Команди офлайн:

```sh
python3 scripts/test_core.py
python3 scripts/audit_can_network.py /path/to/attached.json
```

Результат локально: **152 CoreChecks + 58 CanDiagnosticsChecks + 23 NetworkAuditChecks + 16 NetworkAuditLogChecks = 249 успішних перевірок**. Java replay використовує незалежний bit oracle, фрагментацію і 11 реальних host-вікон. Python працює з виміряною таблицею/сирими рядками; навмисно зіпсовані маски, перекриття, ранній CRA, зміна протоколу і прихований raw-frame відхиляються.

В `verification/can-stage3-fixture.json` збережено лише audit/events і SHA-256 оригіналу, без MAC/GATT/ідентифікаторів авто. `verification/can-stage3-analysis.json` отриманий прямо з прикріпленого оригіналу. `hardwareInclusionVerified=false` збережено явно. Фізичного автомобіля або Vgate в офлайн-середовищі немає. Результат GitHub Actions для нового commit наведено в PR #2; workflow `CAN diagnostics tests` також зберігає машинні результати.
