# Fisker Warm · етап 6: інтернет-доставка тесту

Дата перевірки: 15.10.2026. Авто: Ocean 2023 EU, Ocean OS 2.1, PKC 21.3. Фізичних телефонів та автомобіля у середовищі розробки немає.

## Що працює і що ще не доведено

Реалізовано приватний HTTPS relay, два окремі Android-застосунки та перевірений через інтернет цикл `Remote → сервер → Gateway → підписане підтвердження → Remote`. Автомобільних команд немає. У кожному результаті `vehicle=NOT_IMPLEMENTED`; інтерфейс не може показати «Клімат увімкнено».

**Сервіс уже розгорнуто:** https://fisker-warm-test-relay.bogdanlin2.chatgpt.site . Сторінка доступна власнику після входу у його обліковий запис ChatGPT. Платформна авторизація та окремі токени пристроїв захищають API; стороннім доступ заборонений. Купівля домену, публічна IP SIM, переадресація портів, OceanLink Pro та нова платна підписка для цього тесту не потрібні. Доступність/ліміти Sites залежать від облікового запису; це не автомобільний сервіс із гарантованим SLA.

**Межа доказів:** сервер і клієнти протоколу перевірені через справжній HTTPS. Установлення APK на S24 Ultra/окремий телефон, Samsung Doze, заблокований екран, холодний старт телефону, Kyivstar і фізичний USB саме цього Fisker ще потребують приймального тесту. Відстань не є параметром протоколу; покриття LTE і працездатність обох пристроїв необхідні.

## Транспорт і модель довіри

Обидва телефони самі встановлюють вихідні HTTPS-з'єднання із сервером. Gateway використовує long polling до 20 с; Remote опитує статус лише у відкритому інтерфейсі. Це працює за CGNAT без відкритих портів на телефоні. Обрано системний `HttpsURLConnection`: системна перевірка сертифікатів/імені хоста, заборонений HTTP і редиректи, таймаути 12/30 с, обмеження розміру відповіді. Додаткові Android-бібліотеки не потрібні.

1. Власник входить на приватну сторінку налаштування та створює пару. Сервер повертає одноразово два приватні JSON-файли. Ролі мають різні випадкові 256-бітні API-токени та спільний випадковий 256-бітний ключ HMAC. У базі зберігаються лише SHA-256 API-токенів, не їхні значення або ключ HMAC.
2. Remote перед кожною новою тестовою командою просить підтвердження PIN/паролем блокування основного телефону. Відсутність блокування не дозволяє надсилання. Володіння приватною конфігурацією авторизує пристрій на сервері.
3. HMAC-SHA256 охоплює домен протоколу, роль повідомлення, пару, ID, час, TTL, точний тестовий тип і режим. Команди та підтвердження мають різні канонічні форми. MAC не є авторизацією автомобіля. Приватний TLS relay — довірений компонент, який видає початкові ключі; це не модель захисту від скомпрометованого адміністратора relay або захопленого телефона власника.
4. Команда має випадковий 128-бітний ID, TTL 60 с. Remote зберігає ID до передачі; повторна передача використовує той самий ID. Сервер атомарно допускає одну незавершену команду на пару. Коли heartbeat старіший за 75 с, нова команда відхиляється без відкладеної черги.
5. Gateway спершу перевіряє MAC/пару/тип/час, потім фіксує `DELIVERED` у SQLite (`synchronous=FULL`). Далі окремо фіксує `TEST_ACCEPTED`. Outbox повторює підтвердження до їх прийняття сервером. Журнал переживає перезапуск. Збіг ID із іншим вмістом відхиляється.
6. Після аварійного перезапуску запис `DELIVERED` стає `INTERRUPTED_NO_RETRY`. Старий запит автоматично не виконується. Прострочений запит не стає новим після відновлення інтернету. Це захист від повторного **тестового прийняття**, не обіцянка exactly-once фізичної дії майбутнього автомобільного адаптера.
7. Signed heartbeat і підписаний receipt перевіряються Remote самостійно. `онлайн` означає свіжий heartbeat, а не те, що авто прокинулося або готове до HVAC. У разі недоступності сервера показується невідомий стан, а не вигадане виконання.

Конфігурації зашифровані AES-GCM ключем Android Keystore; резервне копіювання застосунків вимкнене. Секрети відсутні у GitHub, APK, діагностичних журналах і результатах тестів. Одноразові приватні конфігурації після імпорту потрібно видалити із завантажень/каналу передачі. Не публікувати їх у GitHub. Серверна сторінка показує активні пари та дозволяє відкликати загублений пристрій навіть після закриття початкової сторінки. Видалення конфігурації лише на телефоні не замінює відкликання пари.

Службовий шлях створення пар, використаний для первинного HTTPS self-test, повністю вилучено з робочого коду. Застарілий тестовий ключ не авторизує жодного owner-запиту; це перевіряється окремою регресією та HTTPS-запитом. Звичайне створення пари потребує браузерної авторизації власника та same-origin запиту. Живий тест перевірив, що підставлений клієнтом заголовок власника не надає доступу.

## Стани інтерфейсу

| Подія | Що дозволено показати | Чого вона не доводить |
|---|---|---|
| `stored=true` | Сервер зберіг тест | Gateway отримав його |
| Підписаний `DELIVERED` | Тест доставлено до Gateway | Завершене прийняття тесту або HVAC |
| Підписаний `TEST_ACCEPTED`, `vehicle=NOT_IMPLEMENTED` | Gateway прийняв тест; автомобіль не викликався | Клімат працює |
| `EXPIRED_REJECTED` / TTL без receipt | Запит прострочено; прийняття не підтверджене | Можна бездумно створити повторний реальний автомобільний запит |
| `INTERRUPTED_NO_RETRY` | Перезапуск, повтор заборонено | Відомий стан майбутньої фізичної дії |

`GatewayEngine.BlockedPkcPort.canSendToVehicle()` завжди `false`. У ньому немає операції відправлення BLE/CAN. Окрема BLE-перевірка лише відкриває й закриває порожній GATT server та читає можливості advertising; PKC-пакетів або advertising для автомобіля немає. `ReadOnlyPolicy` і `HeatSafety` оригінального проєкту залишені без змін.

## Встановлення та короткий приймальний тест

1. Установіть **Fisker-Warm-Remote.apk** на S24 Ultra, **Fisker-Warm-Gateway.apk** — на окремий Android-телефон. Це окремі пакети `com.fiskerwarm.remote` і `com.fiskerwarm.gateway`: вони співіснують із діагностичним застосунком. Підпис — чинний сертифікат власника Lab02, SHA-256 `848edb87d8b74d2c20efd191a0fa3086c2466aa9a1169628826ac8f5fb78983e`. Старий застосунок видаляти не потрібно.
2. Відкрийте приватну сторінку сервера у браузері під своїм ChatGPT-акаунтом. Натисніть **«Створити захищену пару» один раз**, завантажте Remote- та Gateway-файли. Передайте Gateway-файл лише власному автомобільному телефону. У кожному застосунку натисніть імпорт відповідного JSON. Після імпорту видаліть файли. Якщо сторінка недоступна, перевірте, що акаунт — власник цього проєкту, не створюйте іншу пару навмання.
3. У Gateway дозвольте сповіщення, виберіть необмежене фонове використання батареї та мобільних даних. На Samsung додайте Gateway до **«Програми, які ніколи не переходять у режим сну»** і виключіть оптимізацію Android. Для першого тесту не вмикайте енергозбереження/Data Saver. Кнопка налаштування відкриває системний список — дозволи застосовує власник телефону. Натисніть **«Запустити шлюз»**; має залишатися постійне сповіщення.
4. Для першого тесту достатньо приміщення з нормальною температурою: телефон Gateway на мобільному Kyivstar, S24 — на іншій мережі, наприклад домашній Wi-Fi. **Вимкніть Bluetooth на обох телефонах.** Вимкніть екран Gateway, зачекайте 30 хвилин. У Remote натисніть **«CLIMATE ON · ТЕСТ»**, підтвердьте PIN. Успіх: за 60 с видно підписаний `TEST_ACCEPTED`, при цьому явно зазначено, що автомобіль не викликався. Отримання сервером не рахується успіхом Gateway.
5. Вимкніть інтернет Gateway на 90 с. Remote має втратити онлайн-стан не пізніше 75 с плюс наступне оновлення. Новий тест при офлайн-шлюзі відхиляється. Для перевірки втрати зв'язку між відправленням і отриманням вимкніть інтернет одразу після натискання; після 60 с запит прострочений. Після відновлення немає виконання старого тесту; новий ID надсилається лише окремим натисканням.
6. Для дублювання скористайтеся **«Повторити передачу того самого ID»**, поки є незавершений свіжий запит: у журналі одна команда, повторна доставка повертає її результат. Після перезапуску Gateway незавершений запит може стати `INTERRUPTED_NO_RETRY`; це очікуваний захист, а не успіх HVAC.
7. Перезавантажте Gateway, один раз розблокуйте його. Увімкнений раніше шлюз має відновитися. **До першого розблокування після холодного старту зв'язок не обіцяється.** Після примусової зупинки Android потрібно знову відкрити застосунок. Це суттєве обмеження телефона, залишеного без нагляду на багато днів.

Окремий тест після успіху в приміщенні: залишити шлюз у припаркованому замкненому авто, S24 забрати додому, повторити п.4. Авто для інтернет-доставки не потрібне; його сон і USB перевіряються окремо. Не залишати зареєстрований цифровий ключ без окремої перевірки поведінки замикання; цей Gateway цифровим ключем не зареєстрований.

## Живлення — вимірювана частина, не припущення

Підтвердженої документації про постійне живлення USB **саме Ocean OS 2.1 цього автомобіля після глибокого сну** не знайдено. Офіційний посібник та повідомлення власників не є виміром конкретного авто. Не можна переносити поведінку AC/12V розеток на USB. Тому USB не вважається підтвердженим цілодобовим джерелом.

Gateway записує у журнал `POWER`: Unix-час, `plugged`, заряд/шкалу та температуру батареї. Запис робиться при зміні джерела, зміні рівня ≥2 пунктів або черговій події батареї через ≥10 хв; це **не точний періодичний ватметр**. `plugged=0` — батарея; `2` — USB; `1` — AC; `4` — бездротове живлення. На екрані журнал можна виділити/скопіювати; секретів там немає.

Практична перевірка USB без нового обладнання: підключити справний телефон штатним кабелем, запустити Gateway, зафіксувати заряд і час, замкнути авто та не відкривати його ≥60 хв. Після повернення прочитати історію `POWER`: перехід `2→0` до відкриття дверей підтверджує втрату USB; повернення `0→2` під час пробудження не приховує попереднього запису. Відсутність переходу за годину доводить лише це вікно, а не 24/7. Для добової оцінки потрібен окремий 24-годинний контроль. Не підтримувати авто штучно пробудженим заради зарядки телефона.

Для першої короткої перевірки можна працювати від батареї телефона без підключення до авто: його додаткове споживання 12V тоді нуль. Стала робота потребує виміряного енергобалансу. Інтернет long polling, LTE і wakelock споживають енергію; це не режим ultra-low-power. Нижче **сценарії розрахунку, не вимірювання цього Gateway**:

| Середня потужність телефона | Енергія/добу | Автономність при корисних 12 Wh | Еквівалент від 12 V при ККД 85% |
|---|---:|---:|---:|
| 0,5 W | 12 Wh | 24 год | 1,18 Ah/добу |
| 1 W | 24 Wh | 12 год | 2,35 Ah/добу |
| 2 W | 48 Wh | 6 год | 4,71 Ah/добу |

Формули: `E=P×24`; `t=E_usable/P`; `Ah=E/(12×0,85)`. Реальна батарея може бути зношеною; напруга 12V змінюється; робота інших блоків авто тут не врахована. Навіть кілька Ah/добу — суттєве навантаження, якщо DC/DC не підтримує 12V у відповідному режимі. Наявність великої HV-батареї не доводить постійного живлення аксесуара.

Samsung вказує оптимальний діапазон використання 0…35 °C, застерігає від тривалого перебування у гарячому автомобілі. Зимовий мороз також поза цим діапазоном. Телефон — придатний стенд для етапу 6 за нормальної температури, **цілорічну автомобільну придатність не встановлено**. Постійна зарядка, перегрів, здуття чи зношення батареї не вирішуються програмою. Підключення до OBD-живлення, проводки або запобіжників не пропонуються. Автомобільний захищений перетворювач/контролер можна вибирати лише після підтвердження PKC та вимірів живлення.

## PKC 21.3: відсутня ланка

Використано результати етапів 4–5; CAN-сканування не повторювалося. Статичний аналіз SDK показував `remoteVehicleClimateOn_SendCMD`, передачу через BLE GATT та авторизований сеанс із PKC. Це технічне свідчення можливості, **не дозволений незалежний API для нашого власника**. SDK callback і кешоване значення клімату не доводять фактичний свіжий HVAC ON. ECC 7F0/7F8 — діагностичний доступ, не право запуску клімату. Наявність інтернет-шлюзу цю прогалину не закриває.

Незалежне дозволене сполучення з конкретним PKC 21.3 без платного OceanLink Pro не підтверджене. Не доведені: запуск замкненого сплячого авто, останні налаштування, свіжий стан HVAC, штатний timeout/stop. Увесь автомобільний адаптер лишається заблокованим.

**Для активації потрібні всі пункти:**

1. Документований і дозволений власнику SDK/протокол, ліцензійна можливість використати його в Fisker Warm без обов'язкового OceanLink Pro.
2. Процедура owner provisioning, законно видані ключі та відкликання саме для цього автомобіля; чужі VA-ключі неприйнятні.
3. Контракт PKC 21.3 / OS 2.1: BLE ролі, service/characteristics, challenge/session/counters, ABI Android або переносимий протокол.
4. Підтверджена команда лише Climate ON та передумови: замкнено/припарковано/сон, wake, SOC/12V, поведінка авторизації телефона в салоні.
5. Явна гарантія чи вимір, що команда використовує останні налаштування без їх перезапису.
6. Свіже автомобільне підтвердження HVAC ON з походженням/часом, окреме від прийняття PKC або SDK callback.
7. Підтверджені автоматичний timeout, дозволений stop, відновлення після збою та поведінка повторів. Верифікація чинної HeatSafety залишається обов'язковою; жодного її послаблення в етапі 6.

Конкретні технічні питання власнику/постачальнику дозволеного PKC SDK: чи надаєте незалежному власнику ці сім пунктів для `F160808130021.3`, чи потрібна інша PKC-прошивка, чи є обов'язкова абонплата, які точні підтримувані Android ABI та як видається/відкликається обліковий ключ? Запит **не надсилався**. Самостійна інтеграція дозволеного інтерфейсу — наступна автомобільна розробка після отримання цих відповідей; неперевірених BLE/CAN-пакетів у коді немає.

## Вартість і залежності

Додаткова покупка телефона для поточного тесту: **0 грн**, якщо наявний окремий телефон проходить приймання. Додаткова SIM/нова підписка: **0 грн** понад уже оплачуваний безліміт Kyivstar власника; його наявний тариф продовжує оплачуватися як раніше. Трафік не виміряно на телефоні: за близько 4 тис. poll/добу бюджет порядку десятків MB/добу з TLS — планова оцінка, не підтверджений білінг. Відключення/відновлення та слабке покриття можуть його збільшити.

Сервер працює у доступному обліковому записі Sites; сторонній платний брокер/підписка не потрібні. Платформа ChatGPT Sites і її приватний доступ залишаються залежністю. Ціна гарантованого довгострокового hosting/SLA та майбутнього PKC SDK не встановлена. Проєкт не обіцяє безкоштовність невиданого PKC-інтерфейсу. Вихідний код relay доступний для перенесення на власний HTTPS-hosting, але це окрема конфігурація; сервер не розгорнуто на неіснуючий VPS.

## Перевірки та відтворення

- Оригінальні регресії: 249 перевірок пройдено; ReadOnlyPolicy / HeatSafety мають початкові SHA-256.
- Нове Java-ядро: 26 перевірок, включно з підписами, строками, дисковим відновленням, дублюванням і відмовою журналу. Дисковий тест використовує незалежний Journal; Android SQLite на фізичному телефоні цим не підмінено.
- Relay: 11 Node/SQLite тестів — ролі, ізоляція пар, CSRF, одночасні запити, receipt-стани, повторне відкриття бази, відкликання, розмір запиту.
- Спільний HMAC-вектор Java/JS збігається.
- Остаточний сервер: застарілий службовий ключ отримує HTTP 403 OWNER_REQUIRED; усі 3 службові тестові пари відкликано. Розділ `/api/relay` побайтово не змінено після первинного інтернет-тесту.
- Справжній HTTPS: 25 перевірок двома клієнтами; 8,586 с на доставку через long polling у цьому середовищі. Реально очікували TTL 60/75 с, перевірили відсутність доставки простроченого тесту, відкликали тестову пару. Це не вимір затримки Kyivstar/Samsung.
- Android APK компілюються офіційними SDK 35 / Build Tools 35.0.0 / JDK17; apksigner перевіряє чинний pin сертифіката, aapt2 — пакети/permissions. У build evidence вказано точний sourceCommit і SHA-256 кожного APK. Без фізичних смартфонів не підтверджуються установка, екран off, OEM battery management і реальний reboot.

Локально: `python3 scripts/test_core.py`, `python3 scripts/test_internet.py` (JDK17 + Node24). CI: `.github/workflows/stage6.yml`. Збірка: відновити **існуючий** ключ власника через Actions secrets, вибрати профіль `scripts/select_signing_profile.py`, запустити `scripts/build_internet_apks.py --profile lab02`. Нові ключі не створюються. Старий діагностичний manifest/applicationId незмінні. Секрети ніколи не включаються в artifacts.

Живий self-test: `scripts/test_deployed_relay.py` отримує приватну конфігурацію тільки через прихований stdin, не argv/файли. Остаточний сервер не має службового provision-доступу: для нового повного тесту потрібна окрема пара, створена власником через приватну сторінку, та обидві її конфігурації у полях `remote`/`gateway` stdin. Після тесту власник відкликає цю окрему пару в браузері. `verifyClosed=true` перевіряє, що колишній службовий ключ не працює. Первинні 25 HTTPS-перевірок включали службове створення/відкликання лише одноразових тестових пар до остаточного закриття цього шляху; вони не видаються за виконані фізичними телефонами.

Код: `internet/common`, `internet/android`, `internet/remote`, `internet/gateway`, `internet/relay`. Останній містить повні джерела Vinext/D1 і lockfile; canonical deployed backend source прив'язаний до окремого приватного Sites Git та його saved version. Приватні runtime-секрети не містяться в `.openai/hosting.json`.
