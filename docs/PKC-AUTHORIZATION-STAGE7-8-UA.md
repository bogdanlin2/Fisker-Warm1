# Fisker Warm — авторизація PKC 21.3, етап 7.8

20.10.2026, Europe/Kyiv. Автомобіль: Ocean 2023 EU, OS 2.1, PKC 21.3. Використано актуальний збережений 7.7, докази 7/7.1/7.2, первинний збережений OLP 1.2.6 / ScuSdk, відповідь Chevalier від 13.10 та чинні публічні форми й правила постачальників. IBUS1, CAN-сканування, автомобільні запити й APK поза цим етапом.

## 1. Вердикт

**Авторизацію для власного Fisker Warm не отримано. Реальний запуск клімату не реалізовано. Критерій успіху 7.8 не виконано.**

Дослідження дало конкретніші результати:

1. **`bleKey` і VA-key у дослідженому native-шляху — той самий вхідний секрет.** Це не два послідовні credentials, які треба окремо купити. Відстежено аргумент від Flutter plugin до `connectByVAKey`, декодування 32 hex-символів і встановлення тих самих байтів у `setVaKeyAsByteArray`. Межа доказу — цей клієнт/SDK, не всі режими прошивки PKC21.3.
2. **Підтверджено публічний маршрут первинного власницького доступу до OLP:** правильний запис власника у FOA → відповідне членство/entitlement → реєстрація Undercurrent на тій самій email-адресі → підтримуваний застосунком PKC21-процес. Наявність встановленого PKC21.3 не означає, що новий власник уже має цей обліковий доступ.
3. **Цей маршрут не підтверджує експорт ключа або право/інтерфейс інтеграції Warm.** Прямий індивідуальний експорт через Chevalier Diagnostic Tool і Dittmar уже відхилено. Інший доступ через ліцензіата, зокрема без видачі raw key, залишається конкретним неперевіреним варіантом.
4. У перевірених доступних матеріалах придатного автомобільного секрету не знайдено. Старого OLP-кешу в історії власника немає. Резервний JSON Remote належить тестовому шлюзу й не є PKC-авторизацією.

**Пріоритетна дія:** предметний запит до **Undercurrent із залученням FOA як ліцензіата** про одноразове provisioning або дозволений локальний climate-only інтерфейс для власного Android-клієнта. Готовий [запит англійською](PKC-LICENSEE-REQUEST-STAGE7-8-EN.md) не надісланий. Це питання про інший спосіб доступу, ніж уже відхилений експорт із Diagnostic Tool.

FOB/NFC мають власні механізми доступу; публічна документація цих механізмів не надає незалежного phone → climate provisioning [S9].

## 4. A — FOA / OceanLink Pro: конкретний підтверджений onboarding

Чинна [сторінка членства FOA][S3] відділяє безплатний Registered Owner від платного доступу до OLP. Публічна [форма Undercurrent][S7] містить створення облікового запису з email, ім'ям, паролем та регіоном Europe/North America. Її HTML-шаблон «Registration Complete» не означає, що ми створили або активували акаунт.

Правила FOA вимагають однакову email-адресу в системах FOA/Community/Undercurrent; членство належить людині й не переходить разом з автомобілем [S6]. Якщо VIN уже записаний на іншого власника, [Help Desk][S5] описує перевірку документа адміністратором перед активацією. Документи завантажують у портал; підтвердження власності не потрібно надсилати звичайним листом.

Підтримуваний порядок, **який ще не виконувався для цього власника**:

1. Отримати від оператора підтвердження підтримки вже встановленого **21.3 / OS2.1**, українського власника та потрібної кліматичної функції. Не погоджувати firmware update, reset чи заміну FOB/NFC за замовчуванням.
2. Якщо власник обирає сервіс оператора — встановити правильний запис власника/VIN і entitlement у FOA, використовуючи одну email-адресу. Раніше сплачене чинне членство потрібно врахувати, а не оплачувати повторно без перевірки.
3. Створити/прив'язати Undercurrent account на цій адресі. Реєстрація, право на застосунок, отримання діагностичного grant і фактична PKC-автентифікація мають бути підтверджені окремо.
4. Після окремого погодження автомобільної дії — лише підтримувана процедура Digital Key у чинному OLP. Виробник підтвердив reader через dongle; це не рецепт самостійної реалізації protected routine у Warm. Сторінка розробника перелічує vLinker FD+, але сумісність конкретної FD-IOS firmware з reader не виміряна [S8].

**Статус:** власницький onboarding і призначення продукту **підтверджені первинними джерелами**. Його успіх на цьому VIN не перевірений. Незалежний credential/API для Warm у цю пропозицію публічно не включений. Тому оплачувати її лише з розрахунку на майбутній експорт ключа не обґрунтовано.

## 5. B — сервісне provisioning та доступ через ліцензіата

Повторно прочитано відповідь Chevalier від 13.10: FOA й OVLoop названі ліцензіатами Phone SDK; читання ключа додано до OLP, індивідуальний доступ до raw key не був цільовим сценарієм. Diagnostic Tool не підтримує цей експорт; постачальник також повідомив про відсутність авторизованих окремих інструментів для нього. Dittmar підтвердив відсутність такої послуги своїми засобами. Повторних запитів з цим самим проханням немає.

| Варіант | Статус | Що потрібно для продовження |
|---|---|---|
| Експорт через Chevalier Diagnostic Tool | **Недоступно цим інструментом**, за прямою відповіддю виробника. | Інший підтверджений механізм; купівля цього Tool блокування не усуває. |
| Експорт у Dittmar | **Недоступно в їхній підтвердженій пропозиції.** | Нова конкретна можливість, а не повтор того самого листа. |
| Будь-який інший сервіс, який обіцяє «ключ» | **Технічно можливе, але не підтверджене** owner-export для нашого 21.3. | Пряме підтвердження raw export або підтримуваного доступу Warm, версії, права виконавця, побічних ефектів та ціни. Програмування FOB/NFC або налаштування OLP не є таким результатом. |
| Власний клієнт під дозволом ліцензіата | **Технічно можливе, але не підтверджено як доступна власнику послуга.** | Згода ліцензіата/постачальника, доступна SDK/API або специфікація, дозволений provisioning та прозорі runtime/renewal умови. |
| Локальний climate-only API без видачі raw key | **Можлива архітектура, продукт не встановлений.** | Постачальник має реально надати локальний виклик, власницьке підтвердження, свіжий результат і stop/timeout. У збереженому SDK такого готового owner-bridge не знайдено. |

Публічна [Chevalier Phone Digital Key][S9] прямо описує SDK і сторонні інтеграції. Це нова конкретна підстава звернутися щодо **інтеграції через ліцензіата**, а не повторювати прохання Diagnostic Tool export. Відкрита комерційна ціна, personal-use ліцензія чи підтверджена процедура для одного незалежного Warm не оприлюднені в перевірених матеріалах.

Названий виробником статус «лише для SDK ліцензіатів» — комерційне/продуктове свідчення. Він не доводить криптографічної неможливості незалежного BLE-клієнта з законно отриманим чинним секретом. Водночас наявність APK або декомпільованої бібліотеки не видає ліцензії на включення SDK у Warm; бібліотека сюди не копіюється.

## 6. C — відновлення власних даних

Перевірено доступні назви/вміст релевантних збережених матеріалів і цільові результати підключеної пошти. Для шести діагностичних експортів 03–04.10 пошук назв `bleKey`, `ble_key`, `vaKey`, `va_key`, `credential`, `accessToken`, `refreshToken` не дав збігів. Це **обмежена перевірка**, не побайтове доведення відсутності будь-якого невідомого секрету. Діагностичний inventory сам по собі не є резервною копією цифрового ключа.

Наявний приватний Remote JSON має схему тестового relay і роль remote. Його token/macKey не підставляються в ScuSdk. Значення секретів не включені до цього звіту або GitHub. Відповідей/листів про вже створений FOA/Undercurrent account у цільовому пошуку не виявлено; це не доводить відсутності акаунта на іншій адресі.

Резервної копії старого MyFisker із придатним чинним credential не встановлено. Приватні дані Samsung, Google/Samsung backup datasets і вміст телефона не оглядалися. За [Android Auto Backup][S10] такі резервні дані не є звичайними файлами, доступними іншому застосунку; відновлення застосунку не дорівнює дозволеному експорту PKC-секрету.

**Статус:** готове відновлення з доступних тут даних **недоступне — джерело чинного автомобільного credential не виявлене**. Якщо з'явиться справжній власницький експорт, спочатку перевіряти його походження, тип і актуальність локально, не публікувати ключ і не перебирати випадкові 16-байтові значення. Не пропонується встановлювати старий OLP заради кешу, якого власник ніколи не мав.

## 7. D — чи існує keyless owner enrollment саме у PKC21.3

Твердження FAQ «eliminates the need for a BLE key» зберігається [S11]. Воно не описує ані альтернативного handshake, ані способу делегування кліматичного права сторонньому застосунку. Наш первинний код і пряма відповідь виробника натомість показують використання ключа в OLP. Імовірне пояснення — автоматизація отримання ключа; **це інтерпретація**, не доведена firmware specification.

Новий цільовий статичний аудит розділив входи `key` та `vin+bleKey`: обидва використовують один `performConnection`, який викликає `connectByVAKey`. `runTheConnection` встановлює credential до подальшого вибору сервісу/advertising. Отже, досліджена стара/нова сервісна гілка цього клієнта не є виявленим keyless provisioning. Аргумент VIN тут не породжує секрет.

Дозволений образ або повна діагностична специфікація саме встановленої PKC21.3 залишаються відсутніми серед досліджених матеріалів. З APK не можна встановити всі firmware ACL чи оголосити, що owner-local enrollment ніколи не існує. Публічні описи FOB/NFC [S9] підтверджують інші засоби доступу, але не ланцюг «показати чинний FOB → створити право незалежного phone climate».

FOA-відео [Retrieve Digital Key][S12]: повторно підтверджені автор, назва, 42 s і наявність English ASR track. Текст captions отримати не вдалося (429), тому покрокову процедуру з відео не оголошуємо перевіреною. Воно не підміняє аналіз reader, уже виконаний у 7.1.

**Статус:** незалежний власницький keyless climate/enrollment **технічно не спростований, але не підтверджений**. Для вже простеженого ScuSdk-клієнта вхід без секрету відхиляється. Ці два твердження мають різний обсяг.

Публічні HTTPS-сторінки FOA отримано без входу/надсилання форм. Збережені SHA-256 та вузькі фактичні витяги — у [реєстрі джерел](../verification/stage7-8/authorization-sources.json).

|---|---|---|---|
| FOA Registered Owner | **$0** | $0 за цю реєстрацію | Обліковий запис власника; OLP/PKC credential не включені. |
| FOA Base Quarterly | **$200 за перші 3 місяці** у формі: $100 внеску + $100 першого кварталу | $100/квартал за чинною сторінкою тарифів | Доступ до пропозиції OLP; raw export/незалежний Warm не підтверджені. |
| FOA Base Annual | **$500 за перший рік** у формі: $100 внеску + $400 річного тарифу | $400/рік за чинною сторінкою тарифів | Той самий невирішений окремий дозвіл для Warm. |

Це оголошені USD-суми до індивідуальної перевірки податків, комісій та умов акаунта. Автопродовження керується в FOA Subscriptions; його вимкнення й чинний оплачений період описані в [Help Desk][S5]. Нижчий регулярний платіж не є ціною «отримати довічний ключ». Строк приймання секрету, право його експорту та робота Warm після завершення членства не підтверджені.

Поточний етап не вимагає платного членства, нового телефона, Pulse, Diagnostic Tool або іншого dongle. Нових витрат не зроблено. Підписка не обирається обов'язковою основою проєкту всупереч попереднім умовам власника.

### Дані власника та документи

[Публічні форми FOA][S4] вимагають ім'я, адресу, email, пароль, VIN і прийняття умов; Ukraine є у списку країн, але це не завершена перевірка eligibility. При конфлікті власника VIN FOA називає registration certificate, sales receipt або transfer document [S5]. Завантаження відбувається через обліковий портал після погодження власником; автоматично нічого не передавалося.

Поле receipt у платній формі пов'язане з окремою знижкою для вже придбаного Pulse, а не є вимогою купити Pulse або універсальною вимогою надіслати документ авто. Дані платежу, VIN та документи в дослідженні не вводилися.

## 9. Що потрібно один раз, а що при кожному запуску

| Дія | Частота / залежність |
|---|---|
| Правильний власник/VIN і operator entitlement | Первинний onboarding; повторний перегляд можливий при зміні власника або умов акаунта. Це не кожний BLE-пакет. |
| Provisioning/отримання чинного PKC credential | Первинно, потім за ротації/втрати/відкликання. Фактична політика строку дії 21.3 невідома. |
| Серверний grant дослідженого OLP reader | Потрібний для цього protected reader-flow. Не доведено, що його потрібно викликати для кожного climate start з уже чинним ключем. |
| BLE authentication, challenge/freshness/HMAC | Потрібні у відповідних нових сеансах/повідомленнях. У простеженій native-гілці немає FOA HTTP-запиту на кожний climate виклик. |
| OLP login/членство/offline policy | Залежить від оператора. Збережений 30-денний client offline-limiter не є встановленим строком VA-ключа; він не відключався й не переноситься в Warm. |
| Fresh HVAC feedback, штатний stop/timeout | Потрібні для кожного реального запуску. Callback або локальний кеш не замінюють новий автомобільний результат. |

**Незалежний BLE-клієнт після законного отримання чинного ключа технічно обґрунтований.** Потрібна незалежна реалізація/дозволена SDK, власницьке сховище, перевірені framing/RX та автомобільні interlock. Спостережена відсутність HTTP на кожний виклик підтримує локальну архітектуру; вона не доводить безстроковості ключа, права копіювати SDK або вже підтвердженої роботи на цьому автомобілі.

## 11. Альтернатива при відмові незалежному клієнту

Підтримуваний застосунок ліцензіата — реальний тип продуктової пропозиції; preconditioning для PKC21 заявлений розробником [S8]. Але без експорту або доступного Warm API це **не реалізація власного Fisker Warm**. Платний OLP не обирається необхідною умовою проєкту, а його локальна робота не є вже завершеним інтернет-запуском з будь-якої відстані.

O Loop — інший ліцензіат і закрита платна пропозиція; попередні перевірені обмеження на сторонній API залишаються в [7.7](PKC-IBUS1-DECISION-STAGE7-7-UA.md). Її реклама не дає автоматичної сумісності з поточним 21.3/OS2.1 та не видає ключ Warm. До оновлення автомобіля або нової підписки цей етап не переходить.

Якщо ліцензіати не надають ані credential, ані дозволеного локального інтерфейсу, **саме PKC-архітектура незалежного Warm залишається заблокованою відсутнім способом provisioning**. Це не доведення відсутності всіх режимів PKC чи неможливості клімату загалом. Новий APK, формальний session test або відновлення випадкового backup цю відсутню операцію не реалізують.

## 12. Виконаний аудит і межі результату

- [Офлайн-аудитор](../scripts/audit_pkc_authorization_stage7_8.py) відтворює вузький data flow і звіряє SDK/plugin SHA-256 із попередньою прив'язкою до збереженого APK. [Результат](../verification/stage7-8/sdk-authorization-audit.json) — `STATIC_CREDENTIAL_ALIAS_CONFIRMED_OWNER_NOT_PROVISIONED`. Це не генератор ключів і не перевірка автомобільної авторизації.
- Збережено актуальні публічні ціни/вимоги, факти ownership-review, контакти та межі відновлення. [Реєстр доказів](../verification/stage7-8/authorization-sources.json) не містить секретів або VIN.
- Жодних backend login/diagnostic API-запитів, реєстрацій, password reset, оплат, provider messages, BLE/CAN/UDS або операцій з ECU. ReadOnlyPolicy, HeatSafety і Android runtime не змінені; main/підписи не змінені; APK/Android CI не створювалися. Попередні сотні програмних перевірок не видаються за новий результат.

Відтворення лише статичного аудиту:

```sh
python3 scripts/audit_pkc_authorization_stage7_8.py \
  --smali-root /path/to/retained/apktool/smali \
  --output verification/stage7-8/sdk-authorization-audit.json
```

Публічні форми не заповнювалися. Загальний web-reader повертав для частини FOA URL помилки, тоді як пряме публічне HTTPS-читання цих самих сторінок дало HTTP 200. Тому сайт не оголошується недоступним. Captions 429 не обходилися. Приватні листи, початкові журнали/ключі шлюзу, SDK і повні сторонні HTML до репозиторію не додаються.
