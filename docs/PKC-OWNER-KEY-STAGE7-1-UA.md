# Fisker Warm 7.1 — власний VA/BLE-ключ PKC 21.3

Дата перевірок: 19.10.2026 UTC. Доповнення до [етапу 7](PKC-CLIMATE-ON-STAGE7-UA.md).

**Реальний запуск клімату не реалізовано. Ключ власника не отримано.** OceanLink Pro ніколи не використовувався на цьому автомобілі; відновлення його кешу або раніше виданого ключа не відповідає фактам цього власника.

Новий результат: відновлено видимий клієнтський ланцюг отримання ключа, додатково розібрано шість транспортних функцій і уточнено межу доказу. Серверний SecurityAccess обов'язковий **для дослідженого шляху OceanLink 1.2.6**. Обов'язковість тієї самої послідовності **для всіх дозволених звернень до прошивки PKC 21.3 не встановлена**. Цю відмінність попередній висновок недостатньо чітко пояснював.

## 2. Відновлений ланцюг отримання ключа

Джерела: збережений ARMv7 `libapp.so` OceanLink Pro 1.2.6, попередній Evidence ZIP і новий цільовий розбір [S1–S3]. Це **опис виявленого коду, не інструкція для його виконання на автомобілі**.

| Крок | Код / механізм | Що доведено |
|---|---|---|
| UI → reader | `0xa87fbc → 0xa88b98 → 0xa88ebc → 0xa854ec` | Справжня кнопка читання викликає загальний protected-session helper. |
| Адресація | Helper додає 8 до базової адреси ECU для поля очікуваної відповіді (`0xa85660`); окремо формує `ATSH` із базової адреси. Reader встановлює RX `7AA` (`0xa88ce0`). | Узгоджується з PKC `TX 7A2 / RX 7AA`. Число `7AA` у reader не означає передавання запиту на `7AA`. Перед живим тестом потрібне свіже підтвердження маршруту. |
| Налаштування | Список містить `ATSP6`, default session, `ATWD023E80`, `ATWM1`, `ATCP00`, `ATSH…`, `ATWM3E00`. | Є додаткова автоматизація адаптера. Список не можна копіювати без перевірки: частина налаштувань пов'язана з періодичним передаванням; дієвість на нашому FD-IOS тут не виміряна. |

| Сервер | `0xa85bcc`: `/diagnostics/diag/generate_signature`. Семантика vendor-макросу на конкретному адаптері не підтверджена; це не встановлений альтернативний grant. |
| Extended | Після успішного sendKey надсилається `10 03`, `0xa85ec8 → 0xa87670`, з перевіркою status. | Порядок клієнта: unlock → extended. Це не таблиця дозволів ECU. |
| VA-key | Reader: RoutineControl `31 01 01 10 10` (`0xa88d18/24`): start routine `0110`, option `10`. До приватних діагностичних endpoint не зверталися. Вбудовані backend credentials не використовувалися і не опубліковані. Дозволеного незалежного seed→key алгоритму в досліджених матеріалах не встановлено.

У видимому JSON запиту `generate_signature` немає окремого VIN. Це не доводить відсутності перевірки власності на сервері: він може перевіряти контекст account/token. Отже, звичайний факт власності на автомобіль і право викликати цей приватний API не можна ототожнювати; серверну політику не досліджували активними запитами.

## 3. Усувні залежності та справжня перешкода

| Компонент | Незалежна реалізація / межа |
|---|---|
| BLE до Vgate, ISO-TP/UDS транспорт | Технічно доступні. Адаптер переносить обмін, але не створює право доступу до захищеної routine. |
| UI OLP, relay, `updateblekey` | Не потрібні для локального клієнта з уже отриманим чинним ключем; достатньо локального захищеного сховища. |
| Offline-login 30 днів OLP | Політика дослідженого застосунку. Власний клієнт не повинен її відтворювати; це не доказ безстроковості VA-ключа. Сам OLP не модифікується. |
| HTTP credentials / account grant | Не можна замінити довільним токеном або повторно використати службові константи. Потрібна дозволена сервером інтеграція або доведений штатний ECU-шлях без цього grant. |
| ACL і семантика `0110/10` | **На рівні прошивки не встановлені.** Потрібні точна діагностична специфікація, законно доступний образ PKC для аналізу або окремо погоджені обмежені вимірювання. Нічого не відключалося і не обходилося. |
| Сам VA-key | VIN, Android bond, FOB/NFC credential, SecOC, seed і ключі Remote/Gateway його не замінюють. Потрібен чинний секрет власного PKC. |

Підтримка/ліцензування SDK і криптографічна авторизація автомобіля — різні питання. У перевірених джерелах не знайдено документованого owner-provisioning API, який створює або експортує VA-key після підтвердження власності. Це не глобальний доказ відсутності всіх закритих механізмів.

UDS розрізняє session і security state [S5, S6]. Прийняття extended не означає доступності захищеної routine. Так само порядок клієнта не визначає перевірок усередині конкретного ECU.

## 5. Локальний BLE-клієнт після отримання чинного ключа

**Технічно обґрунтований напрям; середня впевненість щодо реального авто власника.** Докази на рівні SDK сильніші, ніж на рівні фактичного PKC21.3.

Телефон — peripheral / GATT-server, автомобіль — central. Advertising identity похідна від VA-key; повідомлення містять challenge від автомобіля, freshness і HMAC-SHA256 на чинному секреті. GATT-з'єднання або Android bond секрет не замінюють. У дослідженій нативній гілці немає FOA-запиту на кожне з'єднання/кліматичну команду [S1–S3].

Є конкретний кандидат `remoteVehicleClimateOn_SendCMD`, `turnOn=true`, `durationMinutes=15`. Власному клієнту не потрібні UI OLP, login/offline-limiter, server profile, proximity-unlock, керування рухом чи універсальні функції SDK. Копіювання ліцензійного SDK в Warm не виконувалося. Framing/RX, challenge/freshness на обох напрямках і сумісність саме 21.3 потребують перевірки з чинним власним ключем.

Останні налаштування, фактичний HVAC ON і штатний timeout залишаються непідтвердженими. FanSpeed-похідний статус SDK і timestamp читання локального кешу не є самостійним свіжим доказом запуску; це вже встановлено на етапі 7.

## 6. Один наступний практичний тест — PKC session gate

**Лише план для окремого явного погодження власника; не виконувався.** Це активна діагностика, не Read Only. Наявний Warm не змінений і таких запитів не дозволяє. Власнику не пропонується вводити їх у неперевірений термінал. Після погодження обґрунтований окремий мінімальний інструмент лише для цього сценарію.

Мета: перевірити прийняття extended session з відомого default state **без SecurityAccess**. Не отримувати ключ, не запускати routine, не керувати кліматом. Позитивний результат усуне лише першу невідому залежність.

Передумови: авто нерухоме у P зі стоянковим гальмом, звичайним способом пробуджене, без активних попереджень живлення/ключа. Власник поруч із фізичним ключем; двері розблоковані, ключ не залишають усередині. Інші діагностичні застосунки закриті. Не проводити під час руху, оновлення чи сервісу; жодних автоматичних wake/TesterPresent або фонових повторів.

Сценарій **після окремого погодження**:

1. На `TX 7A2 / RX 7AA` один звичайний `22 F1 95` має дати свіжий `F160808130021.3`. Інша identity, старі байти, помилка або відсутність відповіді — зупинка до зміни сесії.
2. Один `10 01` із `50 01` встановлює default baseline на цьому PKC. Без підтвердження не продовжувати. Запит seed відсутній.
3. Один `10 03`; записати RX-ID, точну відповідь і monotonic timestamps. Не повторювати TX. `7F 10 78` означає очікування, не успіх; загальний бюджет приймання — 10 секунд. Якщо отримані коректні P2/P2*, врахувати їх у межах цього бюджету.
4. Один cleanup `10 01` при доступному каналі; `50 01` підтверджує повернення. Потім один `22 F1 95` перевіряє звичайний зв'язок; завершити. Максимум п'ять UDS-запитів у всьому тесті, без додаткових дослідницьких команд при помилці.

Не передбачені `27`, `31`, `11`, programming sessions, записи, reset, seed/key attempts, BLE/HVAC-команди. ELM/ISO-TP режим та відновлення адаптера потрібно зафіксувати в майбутньому інструменті; налаштування passive raw-CAN capture і bootstrap OLP не переносяться. Додавання рядка в чинний Read Only застосунок не є готовим тестом.

| Результат кроку 3 | Дозволений висновок |
|---|---|
| Валідний `50 03` від `7AA` | Extended прийнято у цьому контрольованому стані без попереднього SecurityAccess тестера. Для сучасного UDS очікуються ще чотири байти P2/P2* [S5]. **Не доводить** дозволу routine, експорту VA, відсутності всіх інших authorization states або запуску HVAC. |
| `7F 10 33` | Поточний запит відхилено з securityAccessDenied; без легітимного credential не продовжувати. Не доводить, що платна передплата — єдиний шлях назавжди. |
| `7F 10 22` | Умови ECU не виконані. Зафіксувати стан, завершити; це не доказ серверного блокування. |
| `7F 10 12`, `7E/7F` або інший NRC | Зберегти точний NRC і завершити; не перебирати сесії/рівні доступу. |
| Лише pending, NO DATA, чужий RX, malformed/коротка відповідь | Результат невизначений; спочатку проблема вимірювання/маршруту/стану. Не робити висновку про credential. |

Ризики: пробудження і додаткове споживання 12 V, тимчасова зміна діагностичного/доступового стану PKC, помилка ECU або неповернення сесії. Відсутність write/reset не гарантує відсутності побічних ефектів.

Припинення: Stop/помилка припиняє дослідницькі запити. Якщо правильну identity ще не підтверджено, жодних session/cleanup запитів немає. Після початку session-частини допустимий лише один cleanup `10 01` на підтверджений маршрут, якщо канал доступний. Без `50 01` — «повернення не підтверджено». Закрити інструмент і від'єднати Vgate; без ECU/12 V reset і без припущення про невиміряний S3 timeout. Перевірити звичайний доступ фізичним ключем і стан авто; нові попередження припиняють подальші тести.

Після позитивного gate-test **автоматичного key-read не буде**. Наступний предмет аналізу — permission і побічні ефекти `0110/10` саме цієї прошивки; потрібні firmware/діагностична специфікація або інший достовірний доказ штатної семантики. При security-відмові ця гілка припиняється до отримання легітимного grant. Тест не підмінює отримання ключа.

## 7. Фактично виконані перевірки

- Прочитані фактичні відповіді постачальників, не лише старі проєкти листів.
- На тому самому SHA-256 `libapp.so` повторно запущено pinned Jadart зі збереженим source-derived patch: **10 PASS, 0 FAIL, 5 SKIP**. Пропуски збережені як межі перевірки.
- Нові функції `0xa861f0`, `0xa86f50`, `0xa87670`, `0xa862d8`, `0xa8736c`, `0xa87ab8`: **942 ARM-інструкції** звірені байт у байт з ELF; додатково **8 BL-викликів і 6 маркерів**.
- Переглянуто 57 abstract methods `ScuSdk`, bootstrap credential і спільний HMAC-sender. Це аудит наданої версії, не глобальний доказ відсутності provisioning.
- Повторно пройдено чинні офлайн-перевірки проєкту: **152 core + 58 CAN + 23 group-coverage + 16 Python = 249**. Вони перевіряють програмні обмеження/парсери, а не одержання ключа чи роботу автомобіля. Результат — [JSON](../verification/pkc-stage7-1-core-tests.json).
- Додані [офлайн-аудитор](../scripts/audit_pkc_key_path.py), [його результат](../verification/pkc-stage7-1-key-path-static-audit.json) і [перевірка парсера](../verification/pkc-stage7-1-jadart-verification.json). APK, backend literals, приватні bulk-indices і SDK до репозиторію не додаються.
- `ReadOnlyPolicy` і `HeatSafety` звірені SHA-256 та незмінні. Android runtime не змінений. Автомобільних команд **0**, нових APK **0**, нових звернень до постачальників **0**. `main` та попередні PR не об'єднувалися.

Для відтворення застосувати README Evidence ZIP [S2] до pinned Jadart; зберегти verify у `evidence/verify.json`; запустити `arm32_refs.py`, потім `arm32_dump.py a861f0 a86f50 a87670 a862d8 a8736c a87ab8`. Далі:

```sh
python3 scripts/audit_pkc_key_path.py \
  --analysis-root /path/to/local-analysis \
  --decoded-root /path/to/local-apktool-output \
  --output verification/pkc-stage7-1-key-path-static-audit.json
```

Аудитор не завантажує і не виконує APK, не підключається до авто/сервера й не отримує ключ.

## 8. Практичне рішення

Продовжуємо перевірку **первинного доступу PKC**, використовуючи наявний Vgate для обмеженого gate-test після окремого погодження. Підстав купувати інший інтерфейс, кабель або підписку немає. Інтернет-шлюз поза цим етапом.

Для реального ключа потрібен або штатний діагностичний доступ, який PKC дозволяє власнику без окремого grant, або законно наданий grant для захищеної routine. Який випадок реалізований у встановленому PKC21.3, ще не доведено. Власний BLE-клієнт після отримання чинного секрету технічно можливий; отримання секрету і фактичний CLIMATE ON залишаються невиконаними критичними етапами.
