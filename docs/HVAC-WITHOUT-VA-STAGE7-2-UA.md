# Fisker Warm 7.2 — запуск штатного HVAC без VA/BLE-ключа

Перевірено 19.10.2026 UTC. Автомобіль власника: Ocean 2023 EU, Ocean OS 2.1, PKC 21.3. Доповнення до [7](PKC-CLIMATE-ON-STAGE7-UA.md) і [7.1](PKC-OWNER-KEY-STAGE7-1-UA.md).

**Реальний запуск клімату не реалізовано. Проте знайдено новий конкретний CAN-кандидат, незалежний від дослідженого BLE-шляху OceanLink: штатний сигнал ICC `ICC_ECCSysSwtCmd` у кадрі `0x534`.** Є відкритий код його передавання через внутрішню IBUS1. Сумісність із власним автомобілем, доступ через OBD, право приймання такого запиту ECU та запуск із замкненого сну ще не доведені.

Отже, твердження «для будь-якого запуску HVAC обов'язково потрібен VA-ключ» доказів не має. Водночас знайдений код ще не є працездатним Fisker Warm.

## 1. Що використано без повторення попередньої роботи

- Збережено результати етапів 4/6/7/7.1, історичний діагностичний маршрут ECC `7F0/7F8` та факт відсутності власного VA-ключа. Діагностична відповідь ECC не означає права керування HVAC.
- Chevalier і Dittmar повторно не опитувалися; до їхніх серверів не зверталися. OceanLink на автомобілі власника раніше не використовувався. Старий кеш або чужі ключі не є варіантом.
- `remoteVehicleClimateOn_SendCMD` залишається кандидатом захищеного BLE-шляху, уже дослідженого в 7/7.1. Повторного AOT-розбору тих самих функцій немає.
- `10 03` не виконувалося і не обирається наступним тестом 7.2: воно не перевіряє HVAC ON.
- Перевірено актуальні голови відомих проєктів. Fiskeretta, puddletools/CAN і дві попередньо досліджені HA-інтеграції не дали змін відносно зафіксованого аналізу. Їхні старі результати не видаються за нову перевірку автомобіля [S10–S13].
- Нова підстава для аналізу: публічний `moistpope/oceanfront-view`, зафіксований commit `68a88af90b369c1b2c55d7949c4c848f41deb857`, v1.2, 19.10.2026. Файли отримано через GitHub, звірено з Git blob SHA; стороннє ПЗ не запускалося на автомобілі [S1–S6].

## 3. Новий доказ: штатна кнопка ICC → CAN `0x534`

У [carcatalog.js][S2] `MSG.CLIMATE2` дорівнює `0x534`. Перемикач `climate.on` викликає `cmd.request` із полем `ICC_ECCSysSwtCmd`, значення 1 для On та 2 для Off. Це програмна гілка передавання, а не лише намальована кнопка.

У [похідному DBC][S4] цей кадр має 8 байтів; опис повідомлення вказує **IBUS1, sender ICC**. Поле Motorola start 57, length 2. Словник описує 0 як inactive, 1 як power-on (short), 2 як shutdown (long), 3 як reserved. Назви short/long самі по собі не задають тривалості CAN-імпульсу.

Для **декодування прийнятого кадру**, з індексацією байтів 0–7:

```text
ICC_ECCSysSwtCmd = data[7] & 0x03
```

Це не готовий TX-пакет. Інші байти не можна довільно заповнити нулями.

[cancmd.js][S3] → Android `WebHudApp.canSend` → [CanBridge.kt][S5] → [SocketCAN helper][S6] → `can1/IBUS1` — видимий шлях до шини. За README це CAN-контролери додаткової плати Pulse. Звичайний Android-телефон і його BLE самі по собі такого SocketCAN-інтерфейсу не мають. Vgate під'єднаний до OBD, і рівність його фізичного маршруту IBUS1 ще не підтверджена.

VA, `connectByVAKey` або виклик SDK PKC у цьому ланцюгу не використовуються. Це реальна окрема технічна зачіпка. Однак приймальна політика ECU, маршрутизація gateway і дозвіл виконати дубльовану ICC-команду не випливають із коду відправника.

**Межі та небезпека прямого копіювання:**

1. Encoder починає з initial value **кожного** поля. У цьому ж `0x534` є `ICC_MinChrgSoc_Setting` і `ICC_PwrBattDrvgHeatSwtSts`; їхні initial values — 0. Перше має окремі 254/255 як not activated/invalid, друге 0 означає Off. Тому припущення «усі інші нулі — нічого не змінювати» не доведене. Сторонній кадр може зачепити заряджання/підігрів батареї.
2. Авторський sender повторює подію 3 рази з інтервалом 20 ms. У DBC для `0x534` написано `NoMsgSendType`, тому цей конкретний таймінг не вважається незалежно підтвердженою OEM-вимогою.
3. Наявність CAN-сигналу On/Off для активного HMI не доводить запуск замкненого автомобіля зі сну. У цьому повідомленні немає встановленого 15-хвилинного кліматичного сеансу. Фіксований auto-off і спосіб гарантувати його на сплячому авто невідомі.
4. Відсутність MAC/counter у похідному описі `0x534` не доводить відсутності інших перевірок, залежностей живлення або захистів приймача.
5. Відсутність полів температури/вентилятора в самому On-запиті узгоджується з ідеєю використання поточного стану ECC. **Збереження останніх налаштувань після сну не підтверджене.**

Коміт [2aaa6f5][S14] і актуальний README заявляють live car controls. Це свідчення автора, сильніше за mockup. Оригінальних CAN-логів «вхідний запит → відповідь ECC → фізичний запуск», із версіями ECU, у переглянутому дереві немає. Старий `CAR_CONTROLS_PLAN.md` описує попередній mockup і не є доказом поточного виконання.

Матриці, з яких автор генерує таблиці, названі FM29 IBUS1/IBUS2 V390.1, 20.01.2023. Оригінальні XLSX не входять до переглянутого дерева. Отже, це публічні похідні таблиці, а не підтверджена специфікація встановленої прошивки власника.

## 4. TBOX → VCU: окремий кандидат штатного preconditioning

У тому самому DBC `0x4F8` містить `TBOX_PreCondTriggerReq`. Коментар прямо описує передавання TBOX trigger до **VCU**. На IBUS1 sender позначено GW: спостережуваний mirror не можна ототожнювати з фізичним розташуванням TBOX чи ECC.

| Значення поля | Значення за похідною матрицею |
|---|---|
| 0 | немає запиту |
| 1 | preconditioning батареї |
| 2 | батарея + салон |
| 3 | салон |
| 4 | зупинка preconditioning |

Це конкретна зачіпка для штатної сесії салону, семантично ближча до дистанційного запуску, ніж awake HMI On. **Не встановлені** дозволений зовнішній вхід TBOX/VCU, його автентифікація, процедура пробудження, налаштування салону та умови завершення саме в OS 2.1.

У `0x4F8` також є checksum, alive counter, remote KL15, OTA/flash, charge SOC, travel-mode та інші поля. Їх не можна вгадати або скопіювати як «готову кліматичну команду». Інші повідомлення TBOX мають SecOC-поля, але це не дозволяє без специфікації переносити вимогу автентифікації з одного повідомлення на інше. **Ін'єкція/повторення `0x4F8` не пропонується.**

Роль блоків за доступними доказами: ICC формує штатний HMI-запит; ECC виконує кліматичне регулювання й передає статус; GW маршрутизує/віддзеркалює повідомлення; TBOX має описаний preconditioning trigger до VCU. Остаточний алгоритм дозволу високої напруги/пробудження не відновлено повністю.

## 5. Як відрізнити виконання від доставки

Знайдено статус **ECC `0x373`**, IBUS1, за матрицею через GW кожні 100 ms [S4]. Це нова можливість майбутньої перевірки, а не вже отримане вимірювання.

| Поле | Значення, корисне для перевірки | Межа доказу |
|---|---|---|
| `ECC_CrtSts` | 2 local high voltage, 4 remote working | Саме поле ще треба підтвердити на нашій прошивці. При ручному HMI On не вимагається remote=4. |
| `ECC_WindSpdSts` | 0–7, стан вентилятора | Вентилятор не доводить нагрів. AUTO може тимчасово знизити швидкість до нуля. |
| `ECC_HeatSts` | 0 Off / 1 On | Командний/логічний стан нагріву не замінює вимірювання теплого потоку. |
| `ECC_RemSts` | 0 standby / 1 working / 2 fault | Для локального HMI може залишатися standby; не вимагати remote working як критерій цього тесту. |

Доказ для майбутнього активного прототипу має послідовно містити: сформований запит → фактичний TX → ECU feedback/зміна стану → **фізичний повітряний потік і, коли потрібен обігрів, його нагрів**. У native CAN немає встановленого окремого PKC-ACK; вигадувати його не можна. Фізичний запуск після натискання власником штатного HMI підтвердить тільки штатний шлях, а не запуск із Warm.

**Окрема помилка доказовості стороннього коду:** Go helper [S6] зберігає останнє payload і його час друку; timer повторно друкує кеш із новим часом навіть без нового CAN RX. Kotlin/JS сприймають ці рядки як свіжі. Отже, `available`, `awake` і «живий» fan-state можуть продовжувати показувати стан після зникнення реального RX. Навіть наявний тест freshness у цьому репозиторії перевіряє декодер, а не зупинку фізичного RX у helper. Код не переноситься до Warm. Потрібен окремий час **останнього апаратного приймання**, без оновлення від host keepalive.

## 6. Чому інші напрямки поки не дають незалежної команди

**UDS ECC:** історичні `7F0/7F8` доводять діагностичну досяжність. У перевірених матеріалах немає достовірного сервісу/DID/routine для запуску всієї штатної кліматичної сесії з відповідними дозволами, умовами P/сну і auto-off. Актуаторні сервісні тести компресора/насоса — інше завдання. Не надсилаються `2E`, `2F`, `31`, SecurityAccess, reset або невідомі DID.

**Альтернативний PKC:** похідні матриці мають штатні команди Phone BLE/NFC pairing і pairing QR. Це показує задум enrollment, але не встановлює незалежний авторизований протокол та його зв'язок із HVAC. `PKC_RemPwrOnOffReq` описує power-on/off, а не cabin climate. Ці сигнали не активуються; pairing може зачепити чинні ключі. Для дослідженого BLE-клієнта VA необхідний; для невстановленого альтернативного PKC API відповідь **невідомо**, а не «ключ точно потрібен».

**Телематика:** актуальний первинний сайт O Loop заявляє cabin preconditioning, account/VIN activation, $499/рік і onboarding через OS 2.2.3; legacy third-party API закриті [S7]. Це не безплатний незалежний API Warm. Сайт не дає достатнього протокольного доказу, що конкретний climate-виклик на нашій версії проходить через TBOX/cloud, а не BLE. Реклама функції не є виконаним тестом на цьому авто. Підписка чи оновлення не пропонуються як необхідна покупка.

**Інші проєкти:** Freesker підтверджує наявність діагностичних функцій, але не документує необхідний загальний CLIMATE ON; актуаторні тести зазначені окремо [S8]. Виробник Pulse описує внутрішні CAN-підключення [S9], що узгоджується з Oceanfront, але не доводить кліматичну команду через OBD. Відомі HA/cloud-кнопки не відкривають самостійний автомобільний контракт. Не знайти його там — не доказ відсутності альтернатив.

## 7. Один наступний експеримент: пасивна кореляція HMI → `0x534` / ECC `0x373`

**План для окремого погодження власника; не виконувався. Новий APK не потрібен.** Це не CAN-сканування діапазонів і не отримання ключа. Нова причина вимірювання — конкретні ID та поля з нового первинного коду, 30-секундні вікна й навмисні штатні HMI-події замість попередніх послідовних 500 ms.

### Передумови

Автомобіль припаркований у P, стоянкове гальмо, власник із чинним штатним ключем у салоні. Без несправностей живлення/попереджень, без заряджання чи оновлення ПЗ під час досліду. Штатно пробуджений автомобіль; жодних спроб будити його стороннім CAN-пакетом. Записати початкові температуру, fan/AUTO та стан On/Off. Немає потреби їх змінювати. Якщо потік у AUTO не з'явився через нормальну логіку температури, позначити фізичний результат як непевний, не примушувати HVAC.

Використовується наявний Vgate та BLE UART-термінал із журналом, наприклад **nRF Connect for Mobile** з офіційного джерела Nordic [S16]. Він дозволяє запис характеристик, notifications і експорт журналу. Це загальний інструмент спостереження, не нова версія Fisker Warm.

Чинний Warm не має довільного термінала і не дозволяє наведені нові точкові фільтри: `ReadOnlyPolicy`/`PassiveNetworkPlan` не послаблюються. Закрити Warm/Gateway та інші OBD-клієнти, щоб адаптер мав одне з'єднання. Підключатися **лише до vLinker**, не до PKC. Обрати вже підтверджену UART-пару з попереднього GATT-експорту; якщо вона невідома чи неоднозначна — спочатку лише зберегти карту GATT і зупинитися. Не вгадувати writable characteristic за властивістю Write.

### Точна послідовність тільки до адаптера

Увімкнути notifications UART RX. Кожний рядок нижче надсилати окремо, ASCII плюс **один CR (`0D`)**, чекати відповідь і prompt `>`. Жодних інших/періодичних записів або auto-retry. Після `ATZ` очікується banner; `ATI` — рядок версії, `ATRV` — напруга. Для напруги поза чинним консервативним діапазоном 12.2–16.0 V тест припинити; це стоп-умова проєкту, не OEM-поріг дозволу HVAC. Інші конфігураційні команди мають повернути `OK`; `ATDPN` — очікувано `6`. `OK` не вважається доказом фактичної роботи апаратного фільтра.

```text
ATZ
ATE0
ATI
ATRV
ATL0
ATS1
ATH1
ATSP6
ATCAF0
ATCFC0
ATCSM1
ATD1
ATDPN
ATAR
ATCM7FF
ATCF534
ATMA
```

`ATCSM1` залишає silent monitoring, `ATCFC0` вимикає автоматичний flow control. `ATAR` прибирає попередній receive address **до** нових CM/CF; після фільтра його не надсилати. Семантика перевірена за ELM [S15], відповідність конкретної Vgate-прошивки залишається обмеженням. `ATSP6` не перемикає фізичну проводку OBD на внутрішню IBUS1. Жодного `ATSH`, CAN payload чи UDS-запиту тут немає.

**Вікно 1, 30 s:** 0–5 s клімат штатно Off; на 5 s натиснути тільки загальну штатну кнопку HMI On; до 20 s спостерігати реальний потік/нагрів; на 20 s штатно Off; завершити на 30 s. Зберегти відео з видимим таймером або точні часові позначки HMI та фізичного результату. Якщо початково клімат On, спочатку вимкнути його штатно й зафіксувати це.

Поки `ATMA` справді активний, **один CR** припиняє монітор. Дочекатися prompt. Якщо адаптер сам завершив монітор і вже показав `>`, CR не надсилати: на idle prompt він повторює попередню команду. Якщо стан prompt невідомий — від'єднати BLE/адаптер і позначити вікно непридатним, не надсилати пробні символи.

Після підтвердженої зупинки:

```text
ATCM7FF
ATCF373
ATMA
```

**Вікно 2, 30 s:** повторити ту саму штатну HMI-послідовність Off → On → Off. Це друга фаза того самого експерименту, бо адаптер приймає один точний ID за раз. Тому не приписувати часову причинність між кадрами різних вікон. Для кожного вікна окремо є HMI-позначки і фізичне спостереження.

Очікуваний формат прийнятого рядка з header/DLC — `534 8 …` або `373 8 …`, за ним рівно 8 байтів. Повний рядок записувати без відкидання «незмінних» кадрів. Для `0x534` перевірити появу low two bits останнього байта 1 біля On і 2 біля Off; можливі додаткові inactive=0. Кількість повторів не задається як наперед відомий критерій. Для `0x373` перевірити свіжі RX та зміни ECC/fan/heat відповідно до реальної роботи. Адаптерний час/BLE notification — час доставки, не точний CAN timestamp.

### Успіх, негативний результат і припинення

- **Успіх експерименту:** отримані повні `0x534` на власному OBD із відтворюваним зв'язком On/Off, повний супутній payload, свіжі `0x373`, фізично підтверджена штатна робота. Це підтверджує видимість і семантику для цієї прошивки, **не право ін'єкції, не запуск зі сну і не CLIMATE ON із Warm**.
- `534` є, `373` немає: частково підтверджено командний сигнал; зворотний канал/його маршрут ще невідомий. `373` є без `534`: є статус, але видимість команди не встановлена.
- Немає обох: за умови коректного UART/monitor це не дає позитивного маршруту через OBD. Причини — маршрутизація/інша фізична шина, фільтр адаптера чи відмінна матриця. **Це не доказ відсутності HVAC-команди або необхідності VA.** Не переходити до blind TX чи нового обладнання за таким нулем.
- `?`, CAN ERROR, BUFFER FULL, втрачений prompt/notifications, попередження авто чи живлення: зупинити, зберегти raw log, позначити дані неповними. Не збільшувати активність і не повторювати нескінченно.
- Завершення: один CR лише для активного monitor; після підтвердженого prompt `ATZ` (скидання **адаптера**, не ECU), banner/prompt, від'єднати адаптер. Повернути початковий кліматичний стан штатним HMI й дати автомобілю штатно заснути. Сумарне спостереження обмежене кількома хвилинами. Якщо авто показало несправність, припинити без діагностичних reset/clear.

Авторизованість: власник використовує власний штатний ключ і екран; адаптер тільки слухає CAN. Можливі ефекти — звичайне споживання HVAC та пробудженого авто, невелике споживання адаптера, тимчасові налаштування приймача. PKC enrollment, ECU writes, SecurityAccess, RoutineControl, ін'єкція й обхід захистів не виконуються. Перед майбутнім **активним** прототипом потрібне нове погодження вже конкретного кадру, перевірених сторонніх полів, умов ECU та безпечної зупинки.

## 9. Рішення та невідомі

**Обираємо дослідження штатного ICC CAN On/Off, починаючи з описаного пасивного експерименту на наявному Vgate.** Це конкретна нова команда з відкритою TX-реалізацією, без залежності від знайденого VA-reader, без покупки й без звернень до приватних серверів. Вона має менше невідомих для локального awake HVAC, ніж TBOX-preconditioning, але ще не розв'язує locked/sleep запуск.

Відсутня ланка зараз — **підтверджений на власному авто дозволений маршрут до ICC-кліматичної команди та її виконання з контрольованим життєвим циклом**. Спочатку треба встановити видимість/семантику, потім допустимість конкретного активного запиту, побічні поля, умови живлення та зупинку. Якщо OBD не дає позитивного маршруту, потрібні підтверджена схема або наявна авторизована внутрішня CAN-траса; підстав купувати Pulse чи інше обладнання зараз немає.

Залишаються невідомими: точна відповідність матриці версіям ICC/ECC/GW власника; фізичний/логічний OBD-маршрут у кожному напрямку; вимоги приймача до авторизації/counters; штатний повний `0x534` і поведінка інших полів; мінімальні power/wake умови; виконання у замкненому авто; використання збережених налаштувань після сну; штатний timeout і гарантоване вимкнення; наявність незалежного UDS/PKC або дозволеного OEM API, не описаного відкритими джерелами.

**Підсумок щодо ключа:** VA необхідний для вже дослідженого PKC BLE-шляху. Для нового ICC CAN-кандидата VA не бере участі у відкритій реалізації. Для TBOX/OEM та невідомого альтернативного PKC він не доведений як універсальна умова. Працездатний авторизований запуск із нашого застосунку без ключа ще не встановлено; технічна неможливість такого запуску також не доведена.
