# Fisker Warm: дистанційний CLIMATE ON через інтернет

Етап 5, 15.10.2026. Fisker Ocean 2023 EU / Ocean OS 2.1 / PKC 21.3; історично ECC395 24 та ICC390C49. Вихідний commit `dfcad80437a8c1a29ecb6a5c4e774a0390a66973`, гілка `diagnostics/can-overflow-root-cause`, issue #4. Використано актуальний PDF етапу 4 та збережені докази попереднього аналізу, без повторного пошуку CAN ID.

**Вердикт: повністю доведеного шляху, який одночасно виконує всі умови власника, поки немає. Основна відсутня ланка — підтримуваний власнику незалежний інтерфейс PKC 21.3 для start-only, авторизації, locked-sleep wake та справжнього результату HVAC без OceanLink Pro/платного хмарного сервісу. LTE-модем цієї ланки не створює.**

Найкраща умовна архітектура для подальшої реалізації: телефон власника через інтернет звертається до власного вузла зв'язку; встановлений в автомобілі незалежний LTE-шлюз приймає короткоживучий автентифікований запит, виконує підтверджений PKC start-only і повертає свіжий результат автомобіля. Bluetooth у такій схемі лишається внутрішньою ланкою автомобіля. Власнику не потрібно бути поруч, але **цей шлюз і дозволений виконавчий інтерфейс зараз відсутні**.

## Що встановлено про штатну телематику

O Loop публічно заявляє дистанційний preconditioning у своєму застосунку, пакет коштує $499/рік плюс відповідні податки. FAQ прямо повідомляє, що legacy third-party API вимкнені та підтримується лише офіційний застосунок [1]. Тому цей варіант не задовольняє обмеження етапу 5. Безплатного документованого owner API/SDK для Warm у перевірених матеріалах не знайдено.

Наявність TBOX, LTE або інтернету для мультимедіа не означає наявності доступного командного API. Активність SIM/телематичного акаунта саме цього автомобіля, покриття в Україні, право зовнішнього виклику та wake зі сну без підписки не перевірені: журналів/підтримуваного owner API з такими доказами немає. OS 2.1 та діагностична відповідь TBOX не встановлюють ці властивості. Не пропонується підміна eSIM, replay закритих API, витягування токенів або зміна прошивки.

Старі MyFisker Home Assistant проєкти описують колишній reverse-engineered API і проблеми після відключення cloud, а новий Ocean Pulse використовує інший device API [2]. Доступність старого коду не відновлює сервіс і не є дозволом на актуальну сторонню інтеграцію. На точному стані `ee9cac24…48c7f2` Pulse-клієнта з етапу 4 змін немає: alpha-попередження і тестова телеметрія на status HTTP 401 залишаються підставою не приймати його за доказ реального запуску.

## Конкретний механізм клімату: що відомо, а що ні

Збережений аналіз OceanLink Pro 1.2.6 містить `remoteVehicleClimateOn_SendCMD`: зовнішній одержувач — PKC; локальний транспорт — GATT server на стороні телефона/майбутнього шлюзу, PKC як central. Start має прапорець і тривалість, без аргументів температури/вентилятора. Це статичний доказ реалізації в дослідженому SDK, не автомобільний тест [3].

| Властивість | Наявний доказ | Чого бракує для власного шлюзу |
| --- | --- | --- |
| Одержувач | PKC у простеженому SDK-шляху. ECC — профільний контролер клімату. | Повний внутрішній маршрут та точний підтримуваний контракт PKC 21.3. |
| Авторизація | У зразку є VA/BLE credential, challenge/freshness і HMAC; FAQ називає PKC21 модифікацією Chevalier/FOA [3,4]. | Дозволене незалежне provisioning/відкликання credentials без платного застосунку, FOA/cloud-refresh залежності чи обходу захисту. |
| Замкнений сон | Розробник заявляє PKC21 preconditioning [4]. | Підтверджений wake цього авто без відмикання, присутності власника або постійного утримання мереж awake. |
| Останні налаштування | Start-метод не має temperature/fan аргументів. | Документована семантика та автомобільний тест: відсутність прихованого preset/scenario і відновлення збережених параметрів. |
| Фактична робота | У SDK є обробники станів. | Семантика актуального HVAC-running, джерело/час RX, автентичність та новизна даних. SDK success і час читання кешу цього не доводять. |
| Завершення | Знайдені stop та duration у статичних матеріалах. | Автомобільний timeout на 15 хв, який діє після втрати BLE/LTE/живлення шлюзу, та підтримувана зупинка. |

FAQ PKC21 заявляє усунення потреби у BLE key, тоді як досліджений SDK-шлях використовує credential. Це прогалина специфікації, а не доказ відкритого неавторизованого доступу. Також відсутність HTTP всередині окремого SDK-методу не доводить незалежність provisioning, ліцензії чи повного застосунку від сервера. Статичні рядки про offline-інтервал не є гарантією необмеженої роботи [3,4].

Публічного незалежного PKC21.3 SDK/реалізації, яка підтверджує всі шість властивостей, не знайдено. Декомпільований SDK не копіювався; неперевірені payload не переносилися у Vgate. Його історичний доступ до ECC `7F0/7F8` та PKC `7A2/7AA` є діагностичним, не правом запуску.

## Повний шлях власного шлюзу

1. Телефон власника надсилає одну CLIMATE ON дію через інтернет до вузла зв'язку під контролем власника. У запиті: автомобіль, request ID, короткий строк дії, фіксована тривалість 15 хв і підтвердження авторства. Налаштування HVAC відсутні.
2. Автомобільний шлюз підтримує вихідне TLS-з'єднання через власну LTE SIM або доступний Wi-Fi. Вхідна публічна IP-адреса SIM не потрібна: обидва кінці звертаються до доступного вузла. Через CGNAT телефон не може просто відкрити порт шлюзу.
3. Шлюз перевіряє власника, строк дії та одноразовість запиту; читає свіжий стан P/нерухомості/12 V/HV SOC через підтверджене джерело. Потім використовує дозволений PKC wake/start-only. **Саме цей виконавчий і телеметричний контракт відсутній.**
4. Статуси доставки, прийняття автомобілем і реального HVAC-running розділені. Тільки новий достовірний стан автомобіля дозволяє показати «клімат працює». Підпис шлюзу захищає доставку звіту, але сам по собі не доводить правильності/свіжості автомобільних даних.
5. Автомобіль сам завершує 15-хвилинний сеанс незалежно від хмари/телефона/шлюзу. Підтримувана stop-операція потрібна для відновлення та скасування; завершення підтверджується новим станом.

Власний доступний з інтернету домашній сервер/NAS міг би прибрати плату за relay. Його наявність, uptime і придатний зовнішній доступ у власника не встановлені. Платний VPS не включається в базове рішення: це нова регулярна залежність. Без власного доступного вузла чи дозволеного безплатного relay ця частина також не закрита. Безплатний хмарний тариф не слід вважати гарантованим безстроковим сервісом.

100 км не створюють окремого протокольного обмеження. Потрібні інтернет на обох кінцях, живий шлюз і доступний автомобільний інтерфейс. Підземна стоянка без покриття, відключене живлення або прострочений запит мають давати «недоступно», а не відкладений запуск після відновлення зв'язку.

## Живлення, сон і безпека

Шлюз потребує живлення, яке справді лишається доступним у сні. Не доведено, що USB/розетка цього Ocean підходить; постійне живлення OBD теж не є доказом прийнятного розряду чи дозволеного wiring. Потрібні захищений автомобільний перетворювач, запобіжник, контроль undervoltage та вимірювання всього встановленого вузла. Dev board не є готовим автомобільним блоком. Допустимий монтаж, cold/heat та modem peak-current запас ще не перевірені.

**Особлива умова PKC:** постійний gateway біля автомобіля не повинен сприйматися як присутній ключ, дозволяти небажаний keyless entry/drive або перешкоджати сну. Публічне призначення PKC включає функції ключа [4]. Потрібні climate-only права або підтверджений режим без proximity-функцій. Програмний allowlist запитів не зменшує повноважень самого автомобільного credential, якщо він універсальний.

Нижче математичний додатковий розряд, **не вимірювання Ocean чи обраної плати**. Струм має вимірюватися на 12 V вході з урахуванням LTE і перетворювача.

| Додатковий середній струм | За добу | За 7 діб |
| --- | --- | --- |
| 10 мА | 0,24 А·год | 1,68 А·год |
| 50 мА | 1,20 А·год | 8,40 А·год |
| 100 мА | 2,40 А·год | 16,80 А·год |
| 250 мА | 6,00 А·год | 42,00 А·год |

Формула: `Ah = mA × hours / 1000`. Це не прогноз часу до відмови: стан/ємність батареї, базовий струм авто і робота DC/DC невідомі. Не можна припускати, що HV-батарея безумовно підживлюватиме 12 V. Постійні keep-alive на автомобільних мережах не пропонуються.

Глибокий сон шлюзу економить енергію, але повністю вимкнений модем не отримає негайний запит. PSM/eDRX також мають обмеження доступності й затримок; GSMA прямо описує цей компроміс для відповідних IoT-мереж [7]. Це не доказ підтримки цих режимів конкретною Cat-1 платою чи оператором. Вибирати треба виміряний reachable idle з прийнятним струмом та затримкою, не рекламні мікроампери окремого MCU.

Для мережевої частини потрібні TLS і взаємна автентифікація, окремі від автомобільного credential ключі, захищене зберігання, відкликання доступу, журнал request ID, захист від replay після reboot і rate limit. Черга не повинна виконувати старі/retained команди; дубль після втрати ACK не повинен запускати новий сеанс. За невідомого результату потрібен свіжий стан, а не автоматичний повтор. Вимкнення живлення шлюзу не є способом гарантовано зупинити HVAC — таймаут має виконувати автомобіль.

За сценарію з прикладною платою та окремою Kyivstar SIM опублікована частина першого року: `2767 + 365 × 2 = 3497 грн`, **без** ціни SIM, живлення/монтажу, сервера, розробки й перевищень трафіку. Для додаткової Vodafone SIM це `2767 + 12 × 50 = 3367 грн` за умови вже сумісного основного тарифу, також без перелічених додаткових статей. Повну ціну готового рішення поки чесно визначити не можна. Купувати dev board за цими сумами перед підтвердженням PKC не слід.

Трафік потребує вимірювання. Для масштабу: обмін по 250 байтів в обидва боки щохвилини дає 21,6 МБ за 30 днів **ще без** TCP/TLS, перепідключень, телеметрії та оновлень. Тому не можна оголосити «кілька команд = нуль витрат/трафіку» або гарантувати найменший IoT-пакет.

## Один наступний крок, який відкриває або закриває цей шлях

**Отримати від розробника PKC21.3 підтверджений контракт незалежного owner-operated climate-only шлюзу без OceanLink Pro/платних підписок.** Це вирішальна перевірка до купівлі обладнання. Платний OceanLink Pro не використовується як обов'язкова умова чи тестовий посередник; попередній рекомендований тест через нього з етапу 4 більше не є нашим наступним кроком.

Адресат: Undercurrent Inc / розробник SDK PKC; публічна адреса підтримки **info@undercurrentauto.com** у Google Play. Попросити залучити відповідального розробника Chevalier PKC21 [4,13]. Нижче конкретні запитання; **звернення не надіслане**.

1. Чи дозволено власнику вже встановленого PKC 21.3 використовувати незалежний власний LTE/BLE-шлюз для єдиної CLIMATE ON дії без OceanLink Pro, FOA/cloud-передплати та періодичної серверної перевірки? Які ліцензійні/технічні умови й чи є безплатна документована специфікація/SDK?
2. Як власнику штатно зареєструвати, відкликати й захищено забезпечити credential власного шлюзу? Чим саме PKC21 «без BLE key» відрізняється від VA-key SDK-шляху? Потрібен опис provisioning, не передавання секретів у листі.
3. Яка підтримувана start-only операція для PKC21.3 + ECC39524 + ICC390C49: параметри, GATT-ролі, авторизація/challenge/freshness, успіх і помилки? Чи гарантовано вона не застосовує preset/scenario та використовує останні налаштування автомобіля?
4. Чи працює вона на замкненому автомобілі після підтвердженого сну без unlock, brake/drive-ready і присутності телефона власника? Чи може постійний шлюз залишатися зареєстрованим без keyless entry, proximity-wake та збільшення базового струму? Чи є climate-only credential/режим?
5. Який новий статус означає фактичну роботу HVAC, а не прийняття запиту, обертання лише вентилятора чи читання кешу? Які джерело/час/послідовність RX, одиниці й ознаки достовірності та підтвердження збережених налаштувань?
6. Де виконується 15-хвилинний timeout, що відбувається за відключення BLE/LTE/шлюзу, який дозволений stop і як підтвердити завершення? Які штатні умови відмови за P/швидкістю/HV SOC/12 V?
7. Чи можна надати санітизовану відтворювану демонстрацію саме цієї конфігурації: запит з незалежного інтернет-клієнта, locked-sleep start, збереження двох наборів A/B, новий HVAC-running та самостійне завершення після втрати шлюзу? Без готового клієнта/плати власника — на їхньому підтримуваному стенді/авто.

Позитивний результат цього кроку — дозволена специфікація/provisioning та перевірні дані відповідного виконання. Тоді є підстава обирати шлюз і проводити один повний приймальний сеанс з віддаленим телефоном, без його BLE/локального Wi-Fi доступу до авто. Відповідь «лише наш платний застосунок/хмара», відсутність незалежного credential або тільки маркетингове «preconditioning supported» цей крок не закривають. За таких умов потрібно прямо визнати несумісність поточних вимог із доступним інтерфейсом, а не будувати WAN-обгортку навколо припущення.

## Код, перевірки та результат роботи

В актуальному Warm відсутні `INTERNET`, `BLUETOOTH_ADVERTISE`, GATT-server, HTTP/MQTT relay та автомобільний writer клімату. `SignedEnvelope` — лише офлайн HMAC-примітив із вікном ±30 секунд і callback журналу nonce; це не встановлений сервер, не PKC-авторизація і не реалізація довговічного журналу виконання. `PkcOfflineCodec` також не передає дані автомобілю [3].

Офлайн звірено код, захисні хеші, попередній JSON доказів, математику Ah/трафіку/витрат і виконано наявні 249 перевірок. Вони не підтверджують реального WAN, PKC wake або HVAC. `verification/remote-climate-stage5-evidence.json` зберігає розрахунки, джерела і незакриті перевірки як false. Для документаційного commit запускається CI без APK.

Android-код, `ReadOnlyPolicy`, `HeatSafety` і main не змінюються. Жодної автомобільної команди, купівлі, запиту до control API чи листа постачальнику не виконано. Issue #4 залишається відкритим: повний критерій «100 км → замкнений сон → клімат з останніми налаштуваннями → свіжий результат» поки не доведений.
