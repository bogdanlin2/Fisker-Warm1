# Fisker Warm 0.3.3 — діагностика CAN, 14.10.2026

Ця гілка виправляє доведені помилки приймання й завершення запису та додає вимірювання. Вона **не доводить усунення переповнення на реальному Vgate**, не декодує HVAC і не вмикає опалення. `main` не змінюється, PR #2 залишається чернеткою, Issue #1 залишається відкритим до автомобільної перевірки.

## Що відомо з наданого запису

Журнал `fisker-warm-lab-2026-10-14T05-25-55.849954Z.json` містить OFF та ON: по 45 кадрів, лише ID `0E9`, `adapterBufferFull=true`, `truncated=false`, `comparison.usable=false`. Команди `ATSP6`, `ATCAF0` та `ATCFC0` отримали `OK`. Відмітки завершення сесій розташовані приблизно за 200 мс після підтвердження останньої команди налаштування; це не точний час до внутрішнього переповнення, оскільки журнал не містить timestamp початку ATMA та сирих BLE-пакетів.

У вибірці є коротший п'ятибайтовий payload. Без сирого потоку не можна довести, чи це справжній короткий CAN-кадр, чи обрізаний рядок. Припущення про нього не використовується як доказ причини 45 кадрів.

## Доведені помилки та виправлення

| Старий код | Виправлення та перевірка |
| --- | --- |
| `Stream.finish()` зараховує незавершений рядок як короткий кадр | Незавершені payload відкидаються; `partialLinesDiscarded`, `truncated` і INCOMPLETE. Окремі тести для кінця потоку та prompt усередині рядка. |
| DLC не звіряється з фактичними байтами | DLC має точно відповідати payload, включно з коректним DLC=0. Короткі кадри без DLC з CR залишаються допустимими. |
| Завершення ATMA одразу вимикає приймання, не чекаючи `>` | Приймання триває до фінального prompt або обмеженого тайм-ауту. Зберігається останній повний рядок, навіть якщо він надходить після stop. |
| CR надсилається навіть після `BUFFER FULL` та вже отриманого `>` | Після самостійного завершення команда не повторюється. Для живого монітора залишається одна stop-спроба. Без підтвердження канал закривається для наступних команд. |
| Помилка stop-write ігнорується | `stopError`, `stopWriteConfirmed`, `stopConfirmed`; результат стає INCOMPLETE, повторне використання каналу блокується. |
| Монітор не перевіряє загальний бюджет сесії | Перед ATMA перевіряється дедлайн; acquisition і prompt drain обмежені ним. Пізній start-write та ранній prompt також означають неповний запис. |
| Пошкоджений/довгий рядок може залишити частину payload | Увесь пошкоджений рядок відкидається до роздільника. Документовані ELM NULL-байти ігноруються окремо та рахуються. |
| Створюється проміжний Snapshot/Map на кожен рядок | Кадр додається прямо до одного обмеженого Snapshot. Це усуває зайві об'єкти; вплив на реальну пропускну здатність не виміряний. |
| Ліміт статичного парсера залежить від порожніх рядків CRLF | Порожні рядки не витрачають слот; BUFFER FULL не губиться після ліміту. Ліміт кадрів залишається 1500, вибірок на ID — 12. |
| Actions вимагає текст `TOTAL 151`, тоді як гілка має 152 перевірки | Запускаються обидві реальні Java suites, перевіряються їх exit codes і підсумки; зберігаються журнал та JSON. Діагностична гілка автоматично запускає також підписану Android-збірку. |

Оригінальні три проблеми відтворені на початковому SHA `8bc5634d55ee4e7bd70fa6b71bb62306ef2d1e15`: незавершений кадр=1; неправильний DLC=1; записи при вже готовому адаптері=`ATMA<CR>, <CR>`. Нові тести очікують відкидання цих кадрів та лише один ATMA.

## BLE та налаштування адаптера

Для пасивного режиму додано запит високого пріоритету BLE і MTU 247. CCC записується після завершення MTU-операції; відмова залишає короткі команди в мінімальному payload, зависла операція завершує пробу без накладання GATT-записів. Фактичний MTU записується лише з успішного Android callback. Запит пріоритету позначається як запит, а не як підтверджена швидкість.

Фільтруються callbacks за конкретним GATT та UUID сервісу/характеристики. Write-without-response теж чекає завершення операції Android; таке завершення не видається за ACK периферії. Для ELM важливим залишається його prompt. Дозволені короткі AT/UDS-команди вміщаються навіть у 20 байтів ATT payload. Невідомі UART-сервіси не використовуються.

Пасивна послідовність: `ATZ`, `ATE0`, `ATI`, `ATRV`, `ATL0`, `ATS1`, `ATH1`, `ATSP6`, `ATCAF0`, `ATCFC0`, `ATMA` та, лише для активного монітора, stop-символ CR. Нових команд фільтрації, швидкості UART, перемикання шин чи керування автомобілем немає. `ReadOnlyPolicy` та `HeatSafety` збережені побайтно.

У коді немає фільтра тільки на `0E9`: усі ID `000`–`7FF` приймаються, що перевірено тестом. `ATSP6` задає 11-bit/500 kbit/s; це не перевірка доступу до внутрішньої HVAC-шини. Стан апаратних фільтрів Vgate не прочитаний і не вважається доведеним. Allowlist не дозволяє додати `ATCM`, `ATCF`, порожній `ATCRA`, `ATS0`, `ATBRD` або `ATCS` без зміни захисної політики, тому вони не надсилаються.

## Нові вимірювання в одному JSON

`diagnosticRevision=can-diagnostics-1`; `bleTransport`: MTU, результат його операції, запит пріоритету, тип приймання. `passiveCan`: кількість і розмір BLE-пакетів, байти, час першого/останнього повідомлення, найбільший проміжок, перший BUFFER FULL, кадри/байти на його появі, acquisition/stop drain окремо, незавершені й невалідні рядки, NULL, причина завершення та підтвердження prompt.

Час переповнення — **час отримання статусу телефоном**, з точністю до BLE notification; byte count на цю мить містить цілий пакет. `receivedByteRate` рахує отриманий ASCII потік зі статусами. Він не є CAN bitrate, UART baudrate чи вимірюванням радіоканалу. У новій збірці legacy-baseline без `stopConfirmed` не може дати `usable=true`; потрібно створити свіжий OFF-запис.

## Що залишається непідтвердженим

ELM-подібний `BUFFER FULL` означає втрату даних у буфері адаптера. Швидкість внутрішнього UART, ефективна передача BLE, firmware Vgate, його апаратні фільтри та маршрутизація OBD-шлюзу можуть впливати на результат. Число 45 і один ID не визначають, який із цих механізмів є причиною. Збільшення MTU може не змінити фіксований розмір пакетів Vgate; запит HIGH може бути відхилений. Ці припущення потребують фактичного запису.

Навіть чисті різниці OFF/ON не доводять HVAC: це можуть бути лічильники, таймери й інші системи. `climateStateVerified=false`, `decodedSignals=0`, `climateRunning=null`; опалення заблоковане. Інструмент не може підтвердити повноту всього CAN трафіку лише відсутністю BUFFER FULL.

## Збірка та сумісність

Локально проходять 152 core + 38 CAN regression = 190 перевірок. CAN-тести емулюють адаптер, фрагментацію в кожній позиції, delayed prompt, stop-write failure, межі сесії й пошкоджений потік; фізичного BLE/CAN тут немає. Android компілюється Java 17 з Platform 35 та Build Tools 35.0.0.

Власний попередній APK перевірено через apksigner та aapt2: package `com.fiskerwarm.lab02`, versionCode 7, certificate SHA-256 `848edb87d8b74d2c20efd191a0fa3086c2466aa9a1169628826ac8f5fb78983e`. Діагностичний APK використовує той самий ключ/пакет і внутрішній versionCode 8, без косметичної зміни видимої 0.3.3. Канонічний source Manifest зберігає lab03; сумісний lab02 Manifest формується існуючим профілем збірки. Новий ключ не генерується.

CI перевіряє pinned public identity попереднього APK. Перед передачею готового файла сумісність додатково перевіряється проти фактичних байтів попереднього APK. Підпис v2/v3, zipalign, дозволи та відсутність Internet/services/receivers/providers перевіряються окремо. Приватні ключі/паролі не входять до Git, артефактів або журналів. Артефакти Actions конкретного коміту містять справжні підсумки tests, build-result та apk-inspection.

## Один контрольний тест на Ocean

1. Встановити діагностичний APK поверх 0.3.3, без видалення застосунку. Автомобіль нерухомий у P; залишити його ввімкненим/готовим. Закрити Ocean Read та інші OBD-програми, щоб адаптер використовував лише Fisker Warm.
2. Вимкнути клімат штатним екраном. У Fisker Warm підтвердити стоянку, зробити свіжий **крок 1 / клімат OFF**, обрати той самий `vLinker FD-IOS`, дочекатися завершення.
3. Увімкнути клімат штатним екраном, зачекати приблизно 10 секунд. Виконати **крок 2 / клімат ON** з тим самим адаптером, не згортаючи застосунок.
4. Один раз експортувати фінальний JSON: він включає обидва записи, транспортні вимірювання та comparison.

Для перевірки застосунку очікуються revision `can-diagnostics-1`, фактичні транспортні лічильники та `stopConfirmed=true` в обох записах. Чистий запис вимагає також повного вікна, відсутності BUFFER FULL, невалідних/обрізаних рядків та помилок завершення. Якщо BUFFER FULL повторюється, запис залишається INCOMPLETE/usable=false; наявні часові й байтові дані допоможуть відділити переповнення від обрізання застосунком. Це не означає, що причина переповнення вже встановлена. Не потрібні багаторазові проби чи будь-які діагностичні команди керування.
