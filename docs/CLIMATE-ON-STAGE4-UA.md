# Fisker Warm: CLIMATE ON, етап 4

15.10.2026. Автомобіль: Fisker Ocean 2023 EU, Ocean OS 2.1, PKC 21.3; телефон Samsung S24 Ultra / Android 16; адаптер Vgate vLinker FD-IOS BLE. Досліджений стан Warm: `f8d4b52a1023fbded39c3b1e67f2259a39e3e9b4`, гілка `diagnostics/can-overflow-root-cause`. Завдання: issue #3 з уточненням власника від 15.10.2026, одна функція запуску зі збереженими налаштуваннями.

**Рішення: Vgate залишити для читання. Основний напрям запуску змінити на дозволений власнику прямий BLE-доступ до вже встановленого PKC 21.3. Конкретний метод запуску знайдений у збереженому аналізі OceanLink Pro, але працездатний шлях «кнопка Warm → клімат з останніми налаштуваннями» ще не підтверджений. Новий APK технічно не обґрунтований.**

## Відповіді на п'ять запитань

| Запитання | Встановлений результат |
| --- | --- |
| Хто запускає клімат? | У знайденому локальному шляху зовнішній запит приймає PKC. ECC є профільним контролером клімату; повний внутрішній маршрут, блок остаточного дозволу та відправник повідомлення до ECC не встановлені. Називати ECC єдиним ініціатором або вигадувати ланцюг TBOX → GW → ICC → ECC підстав немає. |
| Чи знайдено CLIMATE ON? | Так, реалізований метод SDK `remoteVehicleClimateOn_SendCMD` і його BLE-шлях. Ні, не знайдено підтвердженої OEM-команди запуску через OBD чи готового авторизованого інтерфейсу для Warm на цьому автомобілі. Це різні рівні доказу. |
| Чи використовуються останні налаштування? | Не підтверджено. У параметрах дослідженого start-методу немає температури, але це не доводить відновлення налаштувань автомобіля. Можливі preset, сценарій або попередні виклики іншого коду застосунку. |
| Чи можна через наш Vgate? | Діагностичний зв'язок з ECC і PKC вже був. Документованого start-запиту та підтвердження результату через цей канал немає. Знайдений SDK-шлях використовує Bluetooth телефона безпосередньо до PKC, а не Vgate. |
| Що потрібно для працездатного Warm? | Підтвердити start-only семантику саме PKC 21.3, дозволене підключення стороннього застосунку, свіжий результат HVAC, пробудження і автомобільний таймаут. Потім інтегрувати один перевірений високорівневий start без setter-ів. Наявних доказів для ввімкнення передачі ще недостатньо. |

## Які попередні результати використані

Повторного сканування CAN, зміни масок чи боротьби з `0E9` не проводилося. Етап 3 встановив правильність 11 груп фільтрів та відсутність позитивного доказу операційного HVAC-трафіку на OBD; це не доводить відсутності самого механізму запуску. Збережені матеріали від 12.10 вже містили точнішу зачіпку: окремий локальний PKC BLE-шлях [1,2].

Історичні відповіді F195 у документації Warm підтверджують PKC `F160808130021.3`, ECC `ECC395 24` та ICC49. Це раніше зчитані ідентичності, не нове опитування 15.10. Загальний напис OS 2.1 не визначає версії всіх ECU. Докази етапу 4 відокремлені у `verification/climate-on-stage4-evidence.json`.

Рівні доказу тут: вимірювання власного автомобіля; збережений статичний аналіз коду; публічна заява розробника; припущення. Жоден статичний метод, рекламна функція чи успішний HTTP-виклик не прирівнюється до вимірювання запуску HVAC.

## Ролі контролерів і межі знань

| Блок | Що підтверджено | Що не встановлено |
| --- | --- | --- |
| ECC | Electronic Climate Control; діагностичні адреси `7F0/7F8`; історична відповідь нашому застосунку [1,3]. | Дозволений start-only сервіс; точні умови прийняття remote start; фінальний арбітраж живлення. |
| ICC | Infotainment Controller; штатний центральний екран дає загальне On/Off клімату [3,4]. | Формат і безпосередній відправник внутрішньої команди до ECC; обов'язковість ICC у remote-шляху. |
| PKC | У SDK знайдено адресата локального BLE start; розробник заявляє preconditioning для PKC 21 [2,5]. | Внутрішній маршрут до ECC, точна реалізація 21.3, сторонній provisioning, застосування останніх налаштувань. |
| Gateway | Центральний gateway і адресна діагностика відомі з попереднього аудиту та Fiskeretta [1,3]. | Чи маршрутизує він потрібну команду запуску з OBD; чи дозволяє її без окремого штатного механізму. |
| TBOX | У каталозі дослідників це Telematics Control Unit [3]. | Публічної OEM-схеми маршруту cabin start саме OS 2.1 / PKC 21.3 немає. Назва блока не доводить, що він обов'язковий для локального PKC BLE. |
| VCU / BCM та живлення | Відомі окремі контролери автомобіля [3]. | Який саме блок дозволяє HV/12 V для цього режиму і які повні заводські interlock-умови. |

Сервісної специфікації Remote Climate Start із повним описом ECU, routing та умов виконання для цієї конфігурації у перевірених відкритих матеріалах не знайдено. DTC-каталог і карта діагностичних адрес не замінюють такої специфікації. Зокрема, скорочення ECC у повідомленнях про пам'ять іншого ECU може означати error-correcting code, а не кліматичний блок.

## Знайдені механізми

### 1. Штатне керування і старий MyFisker

Посібник власника описує загальне On/Off з центрального екрана та анонс керування через застосунок у наступному оновленні [4]. Оригінальний Fisker Product Guide від лютого 2024 описує Remote Climate із цільовою температурою і часом запуску [6]. Це докази задуманої штатної функції, але не специфікація однієї команди зі збереженими налаштуваннями і не доказ нинішньої доступності API для нашого авто.

### 2. Локальний PKC BLE: найконкретніший технічний кандидат

Використано вже збережені `OceanLink-Pro-1.2.6-Report-UA.pdf` та `OceanLink-Pro-1.2.6-Analysis-UA.zip` від 12.10.2026, без повторної декомпіляції. Походження зразка: APKPure, пакет `com.undercurrent.oceanlinkpro`, 1.2.6 / versionCode 130001125, SDK 3.6.2.3.0, ARMv7. Оригінальний XAPK має SHA-256 `b695a7d1…19c28fa`. У попередньому аналізі підписи 20 APK перевірені, але сертифікат не звірений з офіційним еталоном. Цей зразок не запускався на S24 Ultra чи автомобілі [2]. Повні хеші наведені в JSON доказів.

Збережений аналіз простежив шлях: Flutter `remoteVehicleClimateOn` → coroutine wrapper → `ScuSdkImpl.remoteVehicleClimateOn_SendCMD` → `BleGattSendDataHandler.sendDataToPKC` → Bluetooth-повідомлення з автентифікацією. Телефон створює **GATT server**, PKC підключається як central. У простеженому транспорті Vgate не бере участі [2].

Start-інтерфейс має `turnOn` (типово true) та `durationMinutes` (типово 15). Температура, вентилятор і напрямки не є його аргументами. Використовується `_SendCMD`; інший метод `_SendTime` не можна підставляти замість нього. `remoteVehicleClimateOnByName` повертає `NOT_IMPLEMENTED`. Наявність назви методу сама по собі нічого не запускає [2].

Окремий payload з попереднього дослідження не є повним BLE-пакетом і не є підтвердженою командою для ELM/UDS. Його перенесення на `7F0` або `7A2` не обґрунтоване; подібність байтів до діагностичного сервісу не дозволяє виконувати Routine Control. У цьому етапі runnable-пакет або новий transport не додано.

Публічна сторінка розробника в Google Play підтверджує заявлену функцію cabin preconditioning для PKC 21 [5]. FAQ називає PKC21 власною модифікацією Chevalier Tech для FOA, а не стандартною можливістю будь-якого Ocean OS 2.1 [7]. Отже, коректно говорити про використання штатної кліматичної системи через PKC-модифікацію, а не про доведену відкриту заводську команду Fisker.

Авторизація потребує окремого уточнення. Досліджений SDK-шлях працює з VA/BLE credential, challenge, freshness і HMAC. Водночас FAQ PKC21 заявляє усунення потреби у BLE key. Це не доказ відсутності автентифікації і не підстава вимагати від власника витягування ключа: не встановлено, чи йдеться про автоматичний provisioning, інший режим або застарілий опис. Для Warm потрібен **підтримуваний власнику спосіб підключення саме PKC 21.3**, а не вгадування ключів або копіювання SDK.

Суттєві обмеження збереженого аналізу: callback `success(true)` може означати лише завершення програмного виклику, тоді як sender не передав нічого через відсутній challenge. `getClimateState` ставить час читання кешу, а не гарантований час нового повідомлення автомобіля. Повний Flutter AOT-граф натиснення кнопки не відновлений: окремий start-метод не виключає додаткових сценаріїв/налаштувань перед ним [2].

### 3. Ocean Pulse / Home Assistant: конкретна команда, незавершений клієнт

У `MichaelOE/homeassistant-ocean_pulse`, commit `ee9cac2496ac10085db99ae6214e9194c048c7f2`, опис кнопки містить `PKC_CLIMATE_ON` з єдиними додатковими даними `durationMinutes: 15`; є окрема `PKC_CLIMATE_OFF`. Кнопка передає ці дані в `send_command`, який використовує авторизований device API. Це шлях через сторонній Ocean Pulse, не старий MyFisker API і не команда для Vgate [8].

README прямо попереджає про alpha, тестові з'єднання і відсутність Pulse у автора. Додатково в `get_status` за HTTP 401 повертається жорстко задана тестова телеметрія; наступна обробка відкликаного токена після return недосяжна. Отже, поля CLIMATE_ON / SOC / температура з цього клієнта не можна приймати за справжній feedback без перевірки походження. HTTP 200/201 команди також не доводить виконання автомобілем. Жодного запиту до device API у цьому дослідженні не виконано.

Цей код підтверджує існування start-only **контракту клієнта**, але не працездатність сервера, PKC 21.3, використання останніх налаштувань чи необхідність купівлі Pulse.

### 4. O Loop: легітимний канал власника, закрита інтеграція

Чинний провайдер O Loop заявляє cabin preconditioning у своєму застосунку. Водночас його FAQ прямо зазначає вимкнення legacy third-party API та підтримку лише офіційного застосунку [9]. Доступність для конкретного VIN, країни й поєднання OS 2.1 / PKC 21.3 тут не перевірена. Публічного дозволеного API/SDK або app-intent для кнопки Warm не знайдено; контракт «останні налаштування» також не підтверджений. Підписка чи вхід у власний акаунт самі по собі не відкривають право на сторонню автоматизацію. Використання штатного застосунку і можливість інтегрувати його у Warm слід оцінювати окремо.

### 5. Fiskeretta, OBDb та відкриті DBC

Fiskeretta перевірено на commit `2254dbc4…67de7b`, що збігається з уже дослідженим етапом 3. Адреси/діагностика відомі; підтвердженого start-only для ECC у перевіреному коді немає [3]. У OBDb/Fisker-Ocean на `b1e121d4…ff648c` типовий signalset має порожній список commands [10]. Публічний `fisker_ocean_adas.dbc` на `f78f117d…346045` містить ADAS-сигнали, але не знайдено опису cabin climate start [11]. Це обмежений результат пошуку в цих матеріалах, а не доказ неможливості старту в автомобілі.

## Що реально може наявний Vgate

| Перевірка | Результат для CLIMATE ON |
| --- | --- |
| Дістатися до ECU | ECC `7F0/7F8` і PKC `7A2/7AA` історично доступні для адресного читання. Це позитивний факт про діагностику. |
| Передати запит | Сімейство vLinker підтримує ISO 15765-4/raw CAN [12]. Для документованого дозволеного запиту це транспортна можливість, але самого запиту запуску для нашого OBD-шляху не знайдено. |
| Підтвердити прийняття | AT `OK`, prompt, CAN ACK, відповідь на F195 або HTTP/callback success не є підтвердженням виконання HVAC. Дозволений start-response контракт невідомий. |
| Підтвердити реальний клімат | Немає перевірених свіжих діагностичних параметрів HVAC і безпечних станів для цього сценарію. Раніше зафіксовані identity та `0E9` цього не замінюють. |
| Виконати знайдений BLE start | Ні через показаний ELM-канал: це інший адресат і роль BLE. З'єднання телефон → Vgate не реалізує телефон GATT server → PKC. |

Висновок не стверджує фізичної неможливості будь-якого запуску через OBD. Він означає, що **на сьогодні немає доказової основи для такої реалізації**. Купівля іншого ELM-адаптера не усуне відсутність команди й авторизаційного контракту.

## Порівняння варіантів і вибір

| Варіант | Стан доказів | Рішення |
| --- | --- | --- |
| А. Vgate + штатний OBD | Діагностична доступність є; start, результат і право виконання не встановлені. | Залишити для читання. Не обирати основним каналом керування. |
| Б. Авторизована штатна телематика | O Loop заявляє функцію для власника; сторонній API закритий, точна сумісність і last-settings не підтверджені. | Найпростіший заявлений шлях до функції в застосунку провайдера, якщо VIN підтримується. Для Warm потрібен окремий дозволений інтерфейс. |
| В. Внутрішня CAN-мережа | Можливий фізичний доступ не замінює семантику, авторизацію, wake чи timeout. Підтвердженої схеми CLIMATE ON немає. | Резервний напрям дослідження; нове обладнання зараз не купувати. |
| Додатково: прямий PKC BLE | Найточніший наявний start-метод; PKC 21.3 вже встановлений. Авторизована інтеграція Warm і поведінка на авто не доведені. | **Пріоритет наступного дослідження для Warm без нового автомобільного обладнання.** |

Прямий PKC BLE не є хмарною телематикою. Він дає локальний запуск лише в межах підтвердженої Bluetooth-дальності. Запуск з довільної відстані через інтернет потребує дозволеного віддаленого API або окремого авторизованого шлюзу біля автомобіля; такого компонента в наявному комплекті не встановлено. Vgate також не є інтернет-шлюзом.

## Один найбільш інформативний наступний крок

**Один підтриманий розробником PKC контрольний сеанс start-only на цьому автомобілі через авторизований OceanLink Pro / підтримуваний PKC-інтерфейс, із перевіркою останніх налаштувань та санітизованим журналом подій.** Мета сеансу: встановити, чи вже наявний PKC 21.3 дає потрібну однокнопкову поведінку, і чи існує дозволений спосіб викликати її з Warm. Сам факт успіху іншого застосунку ще не дає Warm такого інтерфейсу.

До автомобільної частини потрібне підтвердження підтримуваного start-only шляху саме для цієї комбінації ECU: дозволений provisioning, чи змінює start налаштування, який реальний feedback і який автомобільний timeout. Наявність цієї функції в конкретній авторизованій версії застосунку треба підтвердити, а не пробувати статичний payload. Якщо є лише профіль із температурою або немає дозволеного доступу, сеанс не підміняти guessed-командами; його результат — конкретна прогалина контракту. Звернень до розробників у межах цього етапу не надсилалося.

Після такого підтвердження процедура сеансу:

1. Зафіксувати версії PKC/ECC/ICC та авторизованого застосунку. Авто нерухоме в P, порожній салон, штатні безпечні умови провайдера. Окремо врахувати незмінені вимоги Warm до свіжої автентифікованої телеметрії, 12 V і HV SOC; це вимоги нашої програми, не опубліковані заводські пороги start.
2. На штатному екрані записати набір A з поточних збережених налаштувань: установки зон, AUTO/ручний режим, обраний режим обдуву. Вимкнути клімат штатно, замкнути авто, дочекатися підтвердженого сну; не використовувати вигадані wake-команди. У застосунку не вибирати HVAC preset чи сценарій.
3. Виконати рівно один дозволений start-only на 15 хвилин. Записати час запиту, прийняття і першого **нового** повідомлення HVAC. Контрольне вікно 60 с є критерієм цього тесту, а не заявленою вимогою Fisker. Не повторювати автоматично за невідомого результату.
4. Підтвердити фізичну роботу клімату та новий статус автомобіля. Перевірити, що налаштовані параметри A не підмінені preset-ом. Фактична швидкість вентилятора в AUTO може змінюватись штатно; порівнювати конфігурацію, а не вимагати однакових обертів. Відкривання дверей/поява ключа не повинні бути єдиною причиною пробудження; такі події позначати в журналі.
5. Перервати лише зв'язок телефона і перевірити, що штатний сеанс закінчується автомобілем через запитаний час. Контрольна межа — 15 хвилин плюс 60 с; за відхилення припинити тест підтримуваним способом провайдера або штатним керуванням з автомобіля. Таймер BLE-з'єднання не вважати автомобільним timeout. Окремо перевірити підтримувану зупинку в цьому ж сеансі випробувань.
6. Для розрізнення «останні налаштування» та постійного preset повторити перевірку з відмінним набором B, заданим **вручну на штатному екрані**. Це перевірка семантики збереження; setter-и Warm не створювати. Потрібні два успішні набори, запуск із замкненого сну та підтверджена зупинка. Після завершення відновити бажані налаштування власника.

У журнал включати метод/тип операції, тривалість, часові мітки приймання, джерело і свіжість стану, результат A/B, ознаки сну та фактичного HVAC. Не включати ключі, токени або повні автентифікаційні пакети. Якщо підтримуваний інтерфейс не дозволяє довести відсутність застосування preset перед start, збереження останніх налаштувань лишається непідтвердженим навіть за видимого обігріву.

| Результат сеансу | Наслідок для Warm |
| --- | --- |
| Start з A і B, налаштування збережені; wake/stop/timeout/feedback підтверджені; сторонній інтерфейс дозволений | Є основа для мінімальної інтеграції прямого PKC BLE. |
| Клімат працює, але preset змінює A/B або bare start не виділено | Механізм не виконує поточну вимогу; потрібна підтримувана start-only семантика, а не додавання setter-ів у Warm. |
| Працює тільки розбуджене авто | Є лише частковий start; дистанційний запуск із замкненого сну ще не доведений. |
| Функція працює тільки в закритому застосунку, немає дозволеної інтеграції | Це спосіб користування готовим застосунком, але ще не реалізація Fisker Warm. Не обходити авторизацію. |

## План мінімальної реалізації після позитивного доказу

1. Отримати підтримуваний SDK/API або достатню дозволену специфікацію PKC 21.3 для незалежної реалізації. Спочатку перевірити авторизоване підключення і нову телеметрію без кліматичних команд. Не вбудовувати декомпільований SDK і не витягувати чужі credentials.
2. Реалізувати окремий транспорт PKC, не пересилати BLE-вміст через `ElmChannel`. Для показаного локального варіанта Android потрібні роль GATT server/advertising, контроль життєвого циклу і захищений provisioning. Підтвердити потрібні дозволи й роботу Samsung / Android 16 окремо. Авторизація та свіжі повідомлення мають бути перевірені до start.
3. Одна дія користувача: CLIMATE ON, фіксований сеанс 15 хвилин, без зміни температури/вентилятора/обдуву. Внутрішньо потрібні підтвердження виконання, підтримувана зупинка й автомобільний timeout. Це не розширення до кліматичного контролера.
4. Успіх показувати лише після нового достовірного стану HVAC; прострочена телеметрія, відмова авторизації, disconnect або невідомий результат не повинні показувати «увімкнено». Не повторювати start після timeout зв'язку, доки реальний стан невідомий.
5. Перевірити всі наявні вимоги `HeatSafety`: start, stop, locked-sleep wake, authorization, vehicle-side bound, result feedback і safety telemetry. Нинішні `PRODUCTION_EVIDENCE` усі false. Під поточними незмінними правилами передача лишається заблокованою; створення обходу цих перевірок не входить до плану. Перехід до активного продукту є окремим майбутнім етапом після доказів.
6. Лише тоді обґрунтована збірка з наявними applicationId/signing-профілями. Успішна збірка не замінює приймального тесту автомобіля. Доступ через інтернет оцінювати окремо від локального BLE.

## Виконані офлайн-перевірки та зміни

Повторно перевірено походження збережених матеріалів, їхні SHA-256, 21 запис індексу методів, наявність прив'язок wrapper → `_SendCMD` → sender та роль Android GATT server. Це перевірка збереженого індексу, не нова перевірка оригінального DEX: повних smali у пакеті доказів немає, тому хеші самих методів повторно не обчислювались.

Публічний Python-клієнт Pulse розібрано через AST без імпорту чи виконання його коду: виділені start-only аргументи, шлях кнопки до API та тестова гілка HTTP 401. Фіксовані версії й хеші джерел записані в JSON. Власні ключі, підключення до автомобіля і виклики control API не використовувались.

`python3 scripts/test_core.py`: **249 перевірок пройшли** (152 core + 58 CAN + 23 незалежні Java oracle/replay + 16 Python). Вони підтверджують офлайн-інваріанти, включно з блокуванням активних команд; не підтверджують start чи останні налаштування на авто. CI цього документа перевіряється для точного commit у PR #2; workflow для документаційних змін не збирає APK.

Зміни етапу 4: цей висновок, посилання на нього в README та JSON доказів. Android-код, manifest, `ReadOnlyPolicy`, `HeatSafety`, версія/підпис застосунку не змінені. `main` не змінено, PR #2 не об'єднано. Автомобільних команд у цьому етапі: **0**.
